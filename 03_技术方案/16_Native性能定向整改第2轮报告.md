## 3. 三项整改：做了什么、用了什么数据

### 3.1 历史聚合改走 T-1 预聚合（DIFF-05）

- **投影表**：新增 `report.history_agg_*` 系列表，按刷新批次存储有效学习事实的汇总。存储粒度为单元（人员 × 数据公司 × 是否样例数据），在此之上分三级汇总：数据公司、刷新时的部门、单个人员。
- **刷新**：在一个 REPEATABLE READ 快照内完成，提交时切换为当前批次。入口为 `npm run refresh:history`，seed 后会自动刷新一次。
- **查询**：
  - 每次请求仍实时执行原有的授权编译结果，并实时读取人员当前状态。
  - 一个汇总格子只有在**其中所有单元当前都获得授权**时，才直接用格子的汇总值；部分授权的格子退回到人员级汇总。
  - 授权逻辑和授权规则都没有修改。
- **页面区分 T-1**：`/history` 在 T-1 路径下返回 `historyMode: "T-1"` 与 `dataAsOf`（批次时间）。实时路径返回 `historyMode: "live"`。如果还没有任何已刷新的批次，接口返回 503，不会把实时数据冒充成 T-1。
- **仍走实时路径的部分**：导出（T-15/C04 快照语义不变）、单条明细、依赖单条事实字段的授权来源，以及 Casbin。
- **用到的数据**：合成数据，含 50,000 名主租户人员、1,000,000 条负载事实和 2 条样例事实。T-1 结果与独立真值逐组一致，测量窗口内的所有 HTTP 200 响应都与独立真值比对过，差异为 0。

### 3.2 分析查询与权限/事务查询隔离

- **做法**：每个 API 进程的连接总数仍为 PGPOOL=20，拆成三个池：
  - 权限池 4：token、权威读取、版本检查、范围解析、快照构建；
  - 分析池 12：报表和历史数据读取；
  - 通用池 4：事务、写入、其他业务域。
- **未改动的部分**：连接获取超时 800ms、SQL 超时 10 秒、资源上限都不变。PG 仍为同一实例。
- **理由**：
  - 不选只读副本，因为会增加资源，复制延迟还可能影响 T-16 的"下一请求"语义；
  - 不选在 PG 侧做资源队列，因为 PG 17 本身没有按查询类别分配 CPU 的能力。
  - 分池的作用是让权限读不再排在长时间占用连接的重型分析查询后面。
- **数值来源**：4/12/4 的比例来自本会话容器内的短时对比压测，只用于选参数，不作为门禁证据。

### 3.3 合并每个请求的多次权威读取

1. **一个连接走完整个授权阶段**：每次权限加载/计划只从池里取一次连接，其中的全部权威读取都在这条连接上完成。每条语句和每个版本检查点都保留。
2. **简化中途的两个版本检查**：加载阶段和计划阶段的版本检查，原来各要完整读取一次（3 条语句），现在改为 1 条语句，只读版本号与 schema 版本。
   - 依据：人员、公司授权、成员关系等所有被读取的事实，写入时都会在同一事务里推进版本号。所以版本号不变，就说明完整读取的结果也不会变。
   - 只要有任何不一致，就退回原来的完整读取，因此版本变化时仍得到原来的 403/503。
3. **效果**：热缓存下每个请求的查询数，列表从 14 降到 10，复杂历史从 13 降到 9。这两个数在测量中已核验。
4. **T-16 结论**：T-16 场景结果没有任何变化（见第 5 节）。按裁定 2 第 3 条，本项保留。

## 6. 估算与实测（分开写）

- **实测**：第 2、4、5 节的全部数字，都来自两个证据分支和本报告附带的摘要文件。
- **估算（标明"估算"）**：
