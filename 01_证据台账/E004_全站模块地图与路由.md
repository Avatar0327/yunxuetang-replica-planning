## 1. 架构结论【已验证】
原站为**微前端多子应用架构**：每个业务域是独立部署的前端子应用，拥有自己的路径前缀与 hash 路由。
门户（`/#/`）负责统一页头、应用入口、通知与用户中心。

**规划含义**：这是一个**平台级产品**而非单体应用。按 D-3「单闭环 MVP」，目标产品 V1 **不应复刻这种多应用架构**，应先做单体；但业务对象的边界划分可参考其子应用切分。列入 DIFF-04（有意差异：架构简化）。

## 3. 「全部应用」之外新发现的模块【已验证】
以下 4 个未出现在首页「全部应用」宫格中，仅存在于页头其他区域：
- **审核中心** `/audit-center/#/my-apply` → 平台有**审批流机制**（至少含「我的申请」）
- **下载中心** `/down/#/download` → 导出是**异步任务**，有独立的下载任务中心
- **我的团队** `/o2o/#/myteam` → **主管/团队负责人视角**的独立入口
- **课酬结算** `/te/#/salarysettlement` → 讲师课酬

**【已验证】重要**：「我的团队」的存在说明原站有**主管角色**及其团队数据范围。这是角色权限矩阵的关键行，需重点取证（V-08）。

## 4. 路由命名线索（辅助理解业务边界）
- `o2o` = 培训业务域（线上线下一体化），承载 培训中心/培训规划/我的团队 → **项目/任务属于此域**
- `kng` = knowledge，课程与资源域
- `ote` = online test & exam，考试域，入口是 `queslib`（题库）
- `udp` = user data platform，组织人员域
- `te` = teacher，师资域
- `jf` = 推测为积分（jifen）域

【受限验证】以上命名推断仅作理解辅助，**不作为业务规则依据**，实际边界以各模块页面取证为准。
