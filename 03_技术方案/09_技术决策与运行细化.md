# 技术决策与运行细化

版本：v1.0｜更新：2026-09-23｜技术设计补充；无应用代码、迁移或运行验证。本文细化01～05的工程选择，不改动规划包，已同步T-01～19，不把工程参数写成原站规则。

## 1. 工程决策

| 编号 | 本设计采用 | 理由、代价与验证位置 |
|---|---|---|
| E-01 | pnpm workspace；Vue/后端同仓，统一锁文件；Drizzle加参数化SQL，显式审核迁移 | 适合单人和AI维护；复杂范围查询不受ORM关系装载限制。开发初始化时固定兼容版本，三天预研验证Nest/Fastify/驱动/事务集成 |
| E-02 | UUID v4由服务端生成；业务编号另列；所有分页加稳定ID排序 | 不依赖某一数据库新版本UUID函数；时间查询以业务时间索引实现。PostgreSQL须支持本文使用的NULLS NOT DISTINCT等语法，确切小版本在初始化记录 |
| E-03 | 单体内部采用端口注入，bootstrap装配；跨域用例放workflows | 业务调用可以双向发生，源码与Nest模块不能相互导入实现；避免Authz→Organization→Authz循环 |
| E-04 | 默认READ COMMITTED；受控行锁、乐观版本、唯一约束共同保护写入 | 不把全站事务改成SERIALIZABLE；详情需一次读取同代大纲与进度，多条查询使用短REPEATABLE READ只读事务 |
| E-05 | 事件流序号独立于实体row_version；outbox/inbox持久化 | 一个业务写入可以产生多个事件，不假设每次实体修改都发事件；重放与业务去重分开 |
| E-06 | 学习上报按session_id进行32路HASH分区；账本初期不分区 | 保留会话内全局序号唯一约束；不因按日分区而让跨日重放重复入账。32为本设计起点，压测后通过迁移调整 |
| E-07 | 上传会话和已接收资产分开；完成分片上传后再创建资产事实 | 未上传完的对象不能伪装为已校验资产；支持断点上传、失败重试和孤儿对象清理 |
| E-08 | 运行默认采用托管数据库/Redis、容器服务、私有对象存储/CDN | API与后台进程使用同一后端制品；不引入Kubernetes或独立业务微服务。云厂商/预算在采购前选择 |

E系列是本阶段提出的工程设计，T系列是用户已确认的产品/技术方向。工程预研发现不适配时记录替换原因和影响，不把替换ORM或队列理解为重新决定业务语义。

## 2. 依赖方向与统一授权

允许的源码依赖为：`presentation → application → 本模块domain/端口`；基础设施适配器实现端口；`bootstrap/workflows`负责实例装配及跨模块编排。公共DTO、Port和事件类型放contracts，不能携带ORM实体或连接对象。

例如组织变更需要授权、权限求值又需要组织关系：组织应用服务依赖AuthorizationPort；PolicyService依赖OrganizationFactsPort。两者均只引用接口，bootstrap分别注入PolicyService与组织事实适配器，不使用Nest forwardRef掩盖循环依赖。

OrganizationFactsPort仅由中央策略及其受控范围编译通路调用，用于读当前账号状态、主部门、直属关系、已授权范围成员。它不再次调用PolicyService而形成递归，不接受HTTP客户端传来的“已授权”标记。普通OrganizationPublic查询/命令仍需授权，不能利用事实端口绕过人员数据范围。其结果只服务本次授权或绑定当前权限版本的许可快照。

边界检查必须覆盖：静态import、动态import、模块外repository/实体、跨模块SQL表名和迁移文件归属。每个模块以公开契约替身完成调用方测试；替身只能证明依赖边界，不能替代真实权限SQL测试。跨模块逻辑ID、共享事务和事件依赖列入01的拆分成本表。

## 3. 事务与锁协议

### 3.1 命令提交

有副作用的命令先声明所涉及项目、学习记录、人员/公司/币种及幂等身份，再进入UnitOfWork。锁的固定顺序如下，单模块也必须遵守：

1. 当前调用主体的命令幂等行；已有成功结果直接重放，不再执行业务。
2. 涉及的项目写入屏障，按project_id排序。普通指派/完成持兼容的共享锁；大纲最终切换持排他锁。没有项目上下文的自主学习跳过本步。
3. 涉及的单活会话、学习记录、任务结果，按预先登记的资源类型顺序和ID排序。
4. 所有受影响的人员/公司/币种账户，按tenant_id、data_company_id、person_id(NULLS FIRST)、currency_code、bucket、control_shard固定顺序锁定；创建缺失账户也沿用同一顺序。issuer_control每公司/币种固定64分片，算法及回溯规则见02§10.2；学员余额与待抵扣仍为唯一账户组。
5. 各模块写本模块事实、资格/分录、汇总及审计，再写outbox；同一事务提交。

禁止持有账户锁后再追索新的项目锁；预计算发现新增对象时退出并重新构建命令，不在原事务内反向加锁。大纲预计算不长时间持锁，最终提交才按上述顺序复核。数据库死锁/乐观冲突采用相同命令身份做有界重试；用户需要重新确认的影响变化返回409，绝不自动确认。

外部HTTP、对象存储操作、转码和消息推送均不在数据库事务内等待。一个UnitOfWork中的模块服务只接收受限事务句柄，不得到任意跨schema查询能力。超时或异常须全体回滚；不能返回完成成功后异步补学分。

### 3.2 读一致性

项目详情先固定active_outline_revision_id，再读取这一代的阶段/任务/进度；同一响应不得混入其他代。多条数据库查询时在短只读快照内完成。权限版本按当前请求获取，不能以报表历史快照替代授权。分页cursor绑定查询条件、排序及必要的数据代次；生效或权限版本改变导致cursor失效时返回需刷新，不能串接两个不同授权集合。

T-05的角色并集保留每个授权的节点、动作、字段和范围。T-06派生后台入口及培训中心对应节点，但项目筛选始终在排序、分页、count和导出之前执行。

## 4. 学习事实的分区、去重与归档

`study.progress_event`采用HASH(session_id)分区，主键为`(tenant_id,session_id,client_sequence)`，包含分区键；event_id作为逻辑引用保留。这样相同会话跨业务日、API实例重试、客户端重放仍落在同一分区，由数据库拒绝重复序号。不能改成仅在当天分区内唯一的约束。

会话持久保存`last_accepted_sequence`、最后报文摘要、已确认进度版本、累计接受量和终态。每条热数据上报保存request_hash及ACK摘要；相同序号不同内容返回409，相同序号同内容重放已持久结果，不能重新累计。

清理按以下依赖执行：会话已关闭或已失效 → 无待确认挑战/未提交完成命令 → 归档内容及摘要可校验 → 永久学习结果、权益和会话终态已保留 → 才允许清理热分区中的对应行。活跃或未结算会话不因到达日期而删除。初始热数据窗口按30天估算；实际保留/归档期限在上线运营参数中记录，本轮不执行任何删除。

归档后的旧会话不能重新提交进度。返回会话终态及最后接受序号，若原ACK已不在在线窗口则返回明确的归档/过期结果，不伪造逐条ACK、不把旧包当新学习。需要争议核查时通过受控归档读取，不重新执行完成或发奖。关闭补报仍须满足当前租约与已裁定的故障边界。

账本、权益资格、追回来源及余额对账记录初期保持非分区表，唯一约束永久有效；只有数据量及查询计划证明需要分区，才设计保留全局去重的独立迁移。不得为了清理原始心跳而删除账务或已完成事实。

## 5. 事件可靠交付

`aggregateVersion`描述实体状态，`streamSequence`描述该聚合公开事件流，二者不能共用。业务事务可一次分配多个连续streamSequence，并将多个事件写入outbox；流身份为tenant＋ownerModule＋aggregateType＋aggregateId。

dispatcher按待投递索引分批领取、持租约发送；消费端以consumer＋eventId唯一去重，处理结果和inbox回执在同一事务提交。发送后进程崩溃可重复发送；业务资格唯一键阻止再次发奖。不能把“broker已收取”当成“所有订阅者已处理”。

| 消费类型 | 乱序/缺口处理 | 重建方式 |
|---|---|---|
| 当前状态投影 | 用sourceVersion覆盖；旧版本不回写；必要时拉取拥有方当前完整快照 | 读取快照及变化水位，再接续事件 |
| 浏览/学习等增量事实 | 逐eventId/来源区间落事实；乱序可暂存，不能用最大版本丢弃尚未计入的旧增量 | 从原始事实或归档重建投影 |
| 严格顺序的订阅 | 订阅整个公开流并推进streamSequence；缺口补齐前不宣称最新 | 从拥有方流接口获取缺口或一致快照 |
| 只订阅部分事件类型 | 不因未订阅事件占用了序号而无限等待；游标由完整流投递器推进，或按事实去重处理 | 使用类型过滤前的流游标和明确水位 |
| 账务关键处理 | 完成事务内同步执行；outbox重放只返回既有资格结果 | 对账与显式更正，不广播重发历史奖励 |

重建报表用新generation写旁路投影，追平各来源检查点并核对计数/金额后切换report读指针。原投影在成功切换前继续服务，故障保持旧代并标注更新时间。重建只调用报表订阅者，不能触发奖励、通知或重新指派。

## 6. 上传和媒体资产生命周期

浏览器创建upload_session，服务端固定目标对象键、声明类型/大小/摘要、允许用途和上传者。分片记录part_number、ETag、字节数及校验值；重试同一分片不创建第二个资产。

complete时检查上传者当前权限、分片集合和对象存储返回的实际对象。只有实际大小/摘要核验完成后才创建files.asset，状态为uploaded/processing；上传会话通过result_asset_id关联该资产。媒体探测/扫描/转码成功才置ready，资源和课程才能引用发布。重复complete返回同一assetId，不能生成多个课程或课件对象。

上传取消/过期只标记上传会话，后台清理无有效资产引用的临时对象；删除源对象前必须复核引用及任务状态。处理中失败保留原对象和失败原因供受限重试，不能把失败处理为0时长且继续发布。已发布内容替换使用新资产版本，旧学习/账本仍指向原版本。

逐请求媒体鉴权沿用05的负载模型。CDN票据只是访问凭据，所有新分片请求仍须校验当前授权与内容状态；后台与学员端都不返回可绕开此路径的永久源站URL。

## 7. 运行、发布与恢复

### 7.1 配置和启动

配置分为三类：部署密钥（数据库/Redis/对象存储凭证，从密钥服务或受限环境注入）、工程运行参数（连接池、并发、租约、重试、上报窗口）、业务策略版本（时长、学分、时间/完成规则）。业务参数必须可追溯到生效版本，不靠更改环境变量改写历史口径。未裁定的业务分支不得生成一个看似生效的默认版本。

启动先检查数据库schema兼容版本、必要枚举及唯一约束、对象存储能力和时区；liveness仅说明进程存活，readiness还检查必需持久存储及兼容性。新实例未ready不接流量；后台任务按租约恢复，不能在每个API副本启动时各自跑一份02:00扣减。

### 7.2 发布次序

兼容迁移预演与备份检查 → 单次迁移任务 → 新API实例ready → 旧实例停止接新请求并完成有界事务 → 同版本worker接管任务 → 发布Web静态资源 → 登录/权限/学习/发奖/投影核对。退出中的API不得确认尚未提交的进度；客户端用原序号重试。

expand/contract至少覆盖当前与上一应用版本；旧字段回填校验完成前不删除，生产启动不开启ORM自动同步。迁移由各模块所有者编写，统一执行器按依赖清单排序；应用数据库身份没有DDL权限。回滚应用必须兼容已写的新数据，不用数据库回滚抹掉真实学习与学分。

### 7.3 故障动作

| 故障 | 行为 | 恢复证据 |
|---|---|---|
| PostgreSQL不可用 | 写入不ACK；受保护请求拒绝，页面保留未确认队列 | 恢复后重放幂等命令，账务/序号无重复 |
| Redis故障 | 按用户本轮门禁及04§7.5直接fail closed，不使用L1旧策略或DB降级放行；另设DB降级须独立评审 | 恢复缓存/队列后只用DB当前版本，并与作业检查点对齐 |
| worker崩溃 | 租约到期由同版本worker接管，保留attempt与业务键 | 同一指派、发奖、扣减、导出只产生一次业务结果 |
| CDN/对象存储异常 | 展示媒体暂不可用，暂停有效播放增量；已确认进度保留 | 验权限仍有效后续播，不补造故障期间时长 |
| 投影失败 | 保留上一成功代与水位，显示延迟/错误；不显示虚构0 | 修复后按来源重建并校验人数/时长/来源 |
| 大纲最终提交失败 | 回滚全部状态与账务，旧大纲继续有效，释放/恢复屏障 | 用changeId确认未生效，无部分追回或重复补发 |

恢复目标仍以05的建议值为准：同步主备切换与区域灾难备份恢复分开验证。所有上述故障场景当前均未执行。
