## 2. 核心问题 ✅（用户已确认，2026-09-21）

> **用户原话：主要靠线下面授，缺少基于项目的线上线下融合学习。**

### ⚠️ 这句话改变了批次优先级

「**基于项目的线上线下融合**」在原站的实现恰好是三件事的组合：
```
培训项目（容器）＋ 课程任务（线上）＋ 面授任务（线下）＋ 统一的完成口径与统计
```
- 「培训项目」在**批次 4**
- 「课程」在**批次 2**
- 「**面授**」在**批次 8**

→ **问题**：按当前批次顺序，**要到批次 8 才能解决你的核心痛点**。前面七个批次交付的都是"线上部分"，而你现在已经有线下面授了——**只做线上等于没解决融合问题**。

→ **规划方建议：把面授中心从批次 8 前移，紧随批次 4 培训中心**（或与之合并为"批次 4+"）。
  这样在批次 4 结束时就能交付一条**真正的线上线下融合闭环**：建项目 → 挂线上课程任务 + 线下面授任务 → 指派 → 学员两边都学 → 统一完成判定 → 统计。
  ✅ **已由 D-38 采纳**：面授中心已前移，见交付物 7 的路径 A 批次编排。

### 原推定的四个问题（保留作参考，但优先级须按上述调整）

1. **"谁该学什么"说不清** —— 培训内容与人的匹配靠人工通知，无法按部门/岗位/入职时间自动圈人。
   （原站对应能力：自动加入规则 4 维 + AND/OR + 每天扫描，E011 §4）
2. **"学没学完"看不见** —— 完成情况散落在各处，管理员无法快速判断谁没完成、谁逾期。
   （原站对应能力：学员记录 23 列字段，含必修进度/选修进度/逾期状态，E011 §1）
3. **"学得怎么样"没法证明** —— 缺少可核验的考核与记录，培训效果无法向业务方交代。
   （原站对应能力：考试三层结构、及格线/优秀线双线、首考与补考成绩分列，E014）
4. **"学了有什么用"无激励** —— 学习缺少反馈闭环。
   （原站对应能力：学分/积分/勋章/经验值四套并发，E015 §7.4）

## 3. 业务价值主张

**一条能完整闭合的学习链路**：管理员配置课程 → 按规则指派到人 → 学员在统一入口学习 → 系统自动判定完成 → 管理员看到可信的完成数据。

关键在于**"可信"**：本次调研发现原站在这一点上做得相当扎实——它严格区分了**浏览 / 学习 / 完成**三个层级（E013 §1），区分了**活跃时长 / 学习时长**（E007），区分了**闯关解锁 / 是否必修 / 是否计入完成度**三个正交属性（E008 §4.4）。这些区分不是过度设计，而是"完成率"这个数字能不能被业务方相信的基础。

**目标产品的价值主张即：用更小的功能面，守住同样严谨的数据口径。**

## 6. 成功标准

### 6.1 业务成功标准（基于用户已确认的痛点）

**第一成功标准**：能否用一个培训项目，把**线上课程**与**线下面授**组织在一起，并产出**统一的完成记录与统计**。
这是用户明确的核心痛点，其余指标次之。

### 其余参考指标
| 指标 | 建议目标 | 口径出处 |
|---|---|---|
| 指派覆盖率 | 目标人群 100% 被正确圈入 | 按 E011 §4 的四维规则验证 |
| 必修完成率 | ≥ 80% | 完成率 = 完成人次/覆盖人次（E007 §5） |
| 管理员出报表耗时 | 从"人工汇总"降到"5 分钟内导出" | E013 §9 报表交互模式 |

### 6.2 交付成功标准（可直接验收，不依赖用户补充信息）
1. **闭环可跑通**：管理员建课→指派→学员学习→完成→管理员看到统计，全链路无人工干预。
2. **口径可复核**：交付物 5（指标字典）中每个指标，在系统中都能查到一致的数值。
3. **异常有覆盖**：交付物 8B 的验收场景全部通过，含越权、重复操作、进度丢失、逾期四类异常。
4. **差异有记录**：交付物 8A 的 26 项差异，每项在代码或文档中可追溯到处理方式。
