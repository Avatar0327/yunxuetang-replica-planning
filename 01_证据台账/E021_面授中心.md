→ 目标产品的"学时发放"应抽象为**统一的发放策略机制**，而非每个模块各写一套。列入需求基线。

## 5. ⭐⭐ 考勤设置【已验证】

| 设置项 | 说明 |
|---|---|
| **签到/签退时间范围** | `场次开始前 N 分钟 至 开始后 N 分钟内可以签到`；`场次结束前 N 分钟 至 结束后 N 分钟内可以签退` —— **前后各自可配** |
| **学员需要扫考勤码才能签到** | 二维码核销 |
| ⭐ **开启签到电子围栏** | **地理围栏校验**（防代签） |
| ⭐ **学员请假需要审批** | 含 **`审核流程设置`** 入口 |

### 结论
1. **签到窗口是四个独立参数**（签到前/签到后/签退前/签退后），不是单一容差值。
2. **电子围栏 + 扫码 + 强制签到签退**构成线下防代签体系。
3. ⭐ **「请假」是一等学员状态且带审批流** —— 印证 E018 §6.1 发现的第五种学员身份（签到大屏"不包含请假学员"）。
   → **学员-面授关联对象需包含 `请假状态` 与 `请假审批记录`。**

```
面授完成标准
 ├─ 组合逻辑：满足所有条件 / 满足任意条件（二选一）
```

#### 结论与规划要求
1. **条件项只有两个**，不是开放集合。手册写"考勤完成、考核成绩录入**等**"，实际**没有"等"**——就这两项。

2. **组合逻辑与项目/指派规则一致**（满足所有/任意 = AND/OR），全平台统一。
3. 「录入面授考核成绩」意味着**面授有成绩录入环节**（由管理员或讲师录入），不是学员自己产生。
   → 面授学员记录需含 `考核成绩` 字段与 `录入人`。

## 9. ⭐ 新发现：完成条件与场次考勤的强依赖【已验证】

创建过程中，「面授完成标准」的 **`完成场次考勤`** 选项为**禁用态**（`is-disabled`），悬停提示原文：

> **「所有场次均未设置考勤」**

### 结论
**完成条件「完成场次考勤」只有在至少一个场次启用了「签到」或「签退」时才可选。**

这是**场次考勤设置**与**完成标准**之间的**强依赖与前置校验**，原站在 UI 层就做了约束，而不是等到保存时报错。

**规划要求（写入 REQ-FTF-06）**：
- 完成条件的可选性**依赖前置配置**，需在界面上以禁用态 + 原因提示呈现
- 这个设计值得复刻：**比"选了之后保存时报错"体验好得多**
