#### Important (Should Fix)

1. **R1 — Membership revocation ignores its action's target-person cap.** `src/authz/revision.ts:31` obtains the `administration / authz.membership.revoke` plan, resolves the target membership's person, and checks only `companyCap(a.context)` at line 35 before updating the membership at line 36. It never matches the target person against `a.plan.sources`. A valid revoke grant capped to B can therefore revoke a membership belonging to same-company C; the company check cannot distinguish them. The updated Task4 requirement explicitly covers target-person source scopes/caps during administration mutations. The new person-update and company-grant fixes apply this check, but the existing revoke command remains uncovered. Enforce the union of actual matching sources for this same action against the target person before any mutation, retaining revision locking and company checks. Add both-candidate HTTP negative C/positive B controls with a real narrowed cap, and assert the denied target and dependents remain unchanged. This is an inherited implementation gap newly binding on this task, not an unrelated whole-branch finding. Existing `test/task4-person-cap.test.ts:9` and `test/task4-source-boundary.test.ts:8` cover adjacent commands, not membership revocation.

2. **R2 — Personal attachment bytes bypass the independent download capability.** `src/training/service.ts:29` calls `roster(...)` for both `progress` and `attachment`; roster at line 20 calls `projects(...)` with the default `training.project.view`. Line 33 then returns `bytes: row.attachment`, without ever requesting `training.project.download`. A same-company viewer of P with view but no download can receive P's attachment bytes, and revoking only their download action leaves this new request path working. The registry explicitly separates view/download (`src/authz/registry.ts:6`), and the existing `media()` path uses the download action (`src/training/service.ts:61`). Approved `03_技术方案/03_接口与事件设计.md:93` states read does not imply download; its line 177 treats attachment download separately, and `04_权限模型与三天预研.md:204` requires independent download capability for protected file delivery. Require the download action bound to this project for the attachment branch while retaining person/company/current-state checks; keep progress under its intended view action. Add view-only denial, matching-download success, download scoped to another project denial, and download-only revoke/next-request denial tests for both candidates. `test/task4-company.test.ts:21` uses appointments that include both actions, so its positives and cross-company negatives cannot catch this action substitution.
