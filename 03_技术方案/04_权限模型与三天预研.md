# 权限模型与三天预研

版本：v1.0设计冻结；业务语义已确认。**本轮预研已完成证据交付，结论No-Go：163点通过、5项性能失败，正式B1权限开发未开始。** 本文保留已批准的设计、验证计划和门禁；实际结果以[12预研报告](12_权限预研报告.md)及原始证据为准。

技术底座采用已拍板的方案 A：Vue 3、TypeScript、Element Plus；后端 NestJS + Fastify 的模块化单体；PostgreSQL、Redis、OSS/CDN。权限由同一后端的中央 `authz` 模块管理。推荐以原生集中 `PolicyService` 承载业务语义，以可插拔规则和 `ScopeSpec` 承载扩展；Casbin 仅为待验证的规则执行适配候选，不能据其提供 RBAC/ABAC 功能便认定已经满足本项目。

依据：原包交付物 6；需求基线 REQ-ORG-01～03、REQ-ROLE-01～07、REQ-CAT-01～02；AC-P-01～07；交付物 7 的 B1-05～11。原包保持原样；下述原包冲突、目标产品设计及本轮裁定另行列出，不回写成原站事实。

| 学员管理端 | 无任命及其他管理授权时为0；任命项目负责人后可进入管理后台，仅授予培训中心对应功能和任命项目权限 | 用户T-06已裁定，AUTH-Q2关闭；入口、直链、接口、列表/count和撤销均须验同一规则 |

## 2. 中央 authz 的边界与调用路径

```text
Vue 菜单 / 按钮能力提示
          ↓
Nest Guard（会话、请求上下文、节点与动作映射）
          ↓
业务应用服务 / 领域服务 → PolicyService（唯一业务授权判定入口）
                                ├─ 身份、租户、当前权限版本与硬约束
                                ├─ 角色 / 对象任命 / 分类策略
                                ├─ ScopeSpec → SQL 条件与字段投影
                                └─ 可插拔规则执行器：Native，或预研通过的 Casbin 适配
          ↓
业务仓储（强制接收授权查询计划）→ PostgreSQL
```

`Guard` 只做框架适配，不能在其内部另写一套“管理员放行/主管查部门”的规则。领域服务同样必须强制调用策略，覆盖内部调用、任务队列、批量导入和异步导出；跳过 HTTP 路径不能跳过鉴权。后台系统任务采用明确的服务身份和受限能力，不伪装成无限权限管理员。

策略读取组织事实的内部适配端口与普通业务服务区分：OrganizationFactsPort仅由中央策略编排调用，返回当前上下文内的最小事实，不再次调用PolicyService导致递归；普通人员查询/命令仍必须授权。通过contracts端口和bootstrap绑定实现，避免组织与权限Nest模块互相导入。该内端口不暴露HTTP、不接受客户端的自证授权参数，依赖与测试边界详见09。

建议的契约是设计接口，尚未实现：

| 契约 | 责任 | 不应承担的责任 |
|---|---|---|
| `authorize(context, node, action, resource?)` | 返回允许/拒绝、策略版本、内部原因码、可向用户展示的提示类型 | 不把数据库实体或敏感字段装进错误响应 |
| `buildQueryPolicy(context, node, action, resourceType)` | 输出授权 SQL 所需的 `ScopeSpec`、租户条件、对象条件、字段投影 | 不读取全表后在应用内逐行过滤 |
| `assertCanDelegate(context, proposedGrant)` | 比较同节点动作、数据集合、字段能力及目标角色级别 | 不只比操作名称，不以界面可勾选项作为安全边界 |
| `SubjectResolver` | 把主体类型解析为统一主体关系，例如用户、角色、分类创建者、将来的企课堂成员 | 不要求每个资源查询识别每一种主体类型 |
| `PolicyCompiler` | 中央解释六范围、组合、覆盖与字段语义，生成受控授权计划；模块适配器只将计划映射为本模块字段和参数化查询表达 | 不允许各模块另写范围业务规则，不接受客户端提供的 SQL、部门列表或“已授权”标记 |
| `OrganizationPublic.resolveScopeMembers(ScopeSpec, authzRevision)` | 在指定权限版本下解析所需组织关系，返回版本固定的许可 ID 集或受限关系快照；仅使用中央已确定的范围语义 | 不向调用方暴露 organization 私有表、repository 或任意查询能力，不接收客户端自称已授权的 ScopeSpec |

`ScopeSpec` 是受限、类型化的内部表示，包含租户、节点、业务对象类型、主体锚点、六范围枚举及参数、对象白名单/关系约束、当前权限版本；它不是一个允许任意 SQL 的通用 DSL。业务仓储只能组合编译器产出的可审查条件，不自行复制角色判断。拒绝原因在服务端审计中完整保存；客户端使用不泄露对象存在性、人员名单或跨租户信息的业务提示。

T-07要求ScopeSpec增加服务端计算的公司上限。客户用户的允许公司只有本公司；内部管理者的跨公司范围经authz.person_company_grant授予，仍须节点/动作/对象权限。人员查询绑定当前company_id，历史学习绑定不可变data_company_id。公司上限在SQL排序/分页/count之前应用，ALL_TENANT只省去无意义全员枚举，不能省去公司条件。共同项目内也不得泄露其他公司人数、姓名、个人进度、附件或可领取导出。

项目负责人可管理被任命对象，不意味着有权处理所有参与公司的人员数据。对跨公司项目执行大纲整体生效、批量移除等影响全体人员的命令，必须具备覆盖全部影响公司的管理范围；否则拒绝该整体命令并提示需具有相应范围的管理者处理。仅能查看本公司成员时不得返回全项目个人数据或以隐藏数据完成未授权批量写。内部跨公司授权的新增/撤销与authzRevision同事务，旧下载票据不得继续放行。

中央 `PolicyCompiler` 掌握六范围及组合语义，模块仅提供自己的资源字段映射和查询表达适配；组织事实只经 `OrganizationPublic` 解析。返回的许可集合绑定租户、节点/动作、操作者和 `authzRevision`。`ALL_TENANT` 是执行计划中的全租户标记，直接生成租户谓词，不枚举五万人；物理范围代码仍以02中的 `all` 为准。受限集合可作为服务端绑定的 CTE 参数，或物化为 report 自己的请求暂存许可关系，先与 report 投影在 SQL 中关联过滤，再分页、count 和聚合。构建前后及使用前校验版本；不一致就丢弃旧集合并重建，无法建立当前版本时拒绝。report 不直接 JOIN organization 私有表，不在分页后用人员接口逐条补鉴权。

对外模块门面可命名 `AuthzService`，其内部只委托上述唯一 `PolicyService`，不另建判定规则。动作字典统一采用 `<module>.<resource>.<verb>`，例如 `knowledge.course.update`、`training.enrollment.add`、`report.personal-learning.export`；动作名称与所属节点同时登记，不能只据字符串前缀推导数据范围。

### 2.1 权限概念与 Schema 对应

物理实体、字段和约束统一以02《数据库Schema设计》为准。下表是权限概念到该 Schema 的映射，**不是第二套物理表定义**；统一主体关系和请求许可关系也不因本表出现便新增永久业务表。

| 权限概念 | 02中的对应实体或接口概念 | 最低必要内容与约束 |
|---|---|---|
| 角色与人员角色 | `authz.role`、`authz.person_role` | 租户、角色等级、有效状态；人员与角色多对多，不能只在人员表放一个 `role_id` |
| 节点授权 | `authz.role_node_policy`、`authz.role_node_action`、`authz.policy_department` | 角色、节点、导航、动作/字段能力和范围配置；联合键含租户与节点 |
| 人员级管辖 | `authz.person_jurisdiction` | T-16：绑定具体person_role成员关系，供选MANAGED_SCOPE的节点解析，不覆盖其他六范围 |
| 单人独立覆盖 | `authz.person_node_override`、`authz.override_department` | 所属角色、节点、覆盖内容与生效版本；T-05已定只影响对应角色/节点，不跨角色全局收紧 |
| 对象任命 | `authz.object_appointment` | 同步授权索引；实际对象关系由拥有模块维护，撤销不能等待异步投影 |
| 分类与课程策略 | `knowledge.catalog`、`knowledge.catalog_grant`、`knowledge.course_revision`、`knowledge.course_grant` | 主体、独立动作、公开、继承来源、锁定及课程浏览覆盖模式 |
| 主体类型与成员解析 | `authz.subject_type`、`SubjectResolver` 和拥有模块公开关系接口 | 统一主体成员关系是解析契约，不另建本文件版本的 `subject_membership` 物理表 |
| 部门层级 | `organization.department_closure`，仅由 organization 模块内部访问 | 最多 20 层部门范围，经 `OrganizationPublic` 解析；不用于推导团队 |
| 权威权限版本与审计 | `authz.tenant_authorization_revision`、`audit.audit_event` | 租户级版本与操作者、变更前后、受影响实体、请求关联 ID；人员级修订号如保留只作辅助，不能替代租户权威版本 |

所有可授权对象和关系均带租户键。除主键外，外键与唯一约束也应防止跨租户引用。对象任命不能引用其他租户的用户；前端传来的租户 ID、角色 ID、对象 ID 都需要在当前上下文内重新验证。

## 3. 三维权限、六范围与三级覆盖

### 3.1 三维分别表达，按节点绑定

导航决定普通管理入口是否可达，动作决定能做什么，范围决定操作可作用于哪些数据。一个角色可以在课程管理查看全租户课程，在个人学习详情只看本部门，在部门学习汇总看指定部门。字段能力也绑定节点，例如“个人学习详情可看手机号”不自动允许“考试记录可看手机号”。

普通管理节点要求导航可达且拥有对应动作，再与对象范围相交；导航关闭的普通路径直接访问也拒绝。学员端自身学习能力采用独立节点，不因管理端菜单为0而消失。T-06明确有效项目负责人任命是管理后台及培训中心对应导航的合法来源，即使学员基础角色菜单为0，也应显示并允许进入该后台；项目列表及操作范围仍限任命对象。其他模块及未获授权的培训中心节点继续拒绝，不能把后台入口能力解释成整个培训中心全功能、全项目权限。

动作与范围须成对保留。例：角色 A 允许“编辑自己创建的课程”，角色 B 允许“查看全租户课程”，不能先把动作并为“查看+编辑”、再把范围并为“全租户”，从而意外得到全租户编辑能力。正确输入始终是同一节点、同一动作对应的候选授权集合。

### 3.2 六范围的作用域

| 范围 | 查询语义 | 必须固定的边界 |
|---|---|---|
| 全部数据 | 当前租户内、当前节点和动作可作用的数据 | 不是跨租户；仍满足发布状态、对象类型、字段和其他硬约束 |
| 本部门及下属部门数据 | 当前用户主部门及部门闭包下的人员/对象集合 | 最多 20 层；不是直属下属集合；缺失主部门不能降级为全部 |
| 本部门数据 | 当前用户主部门对应集合 | 不含子部门，不含同级部门 |
| 指定部门数据 | 配置中列出的部门对应集合 | T-16：includeDescendants默认false，显式true才包含子树 |
| 管辖范围内的数据 | 读取当前角色成员关系下有效的人员级管辖参数，再按节点支持的维度解析 | 缺失配置默认无该范围授权；不是对全部六种范围的无条件替换 |
| 自己的数据 | 与本人身份有该节点定义的归属关系的数据 | 人员报表为 `record.person_id = actor.person_id`；课程等节点的“自己”须明确是创建者、上传者或其他关系，不按名字猜测 |

节点须登记自己的合法维度与锚点，例如人员报表用人员集合，课程管理可用所属分类/创建关系，商城分别为商品、商品分类与人员选择范围。不能把任意对象的 `created_by` 统一当作“自己”，也不能把所有六范围机械地套在没有部门归属定义的业务对象上。缺少节点语义定义时应拒绝发布该节点权限配置。

### 3.3 三级结构的已确认解析顺序

在单个角色成员关系内，按T-05/T-16执行以下结构：

1. 读取该角色在该节点的基础范围。
2. 如果最终范围选择“管辖范围内的数据”，读取人员级管辖参数作为其具体集合；若节点明确允许人员管辖作附加上限，必须另有显式配置与已确认规则，不能隐式使用。
3. 该人员在该角色、该节点存在“独立范围”时，用其替代这一角色授权中的基础范围表达；替代后如果仍是“管辖范围”，仍需解析管辖参数。覆盖不凭空增加导航、动作或敏感字段能力，也受授予人的授权上限限制。
4. T-05已确认：多个角色分别计算后，同节点、同动作的合法授权取并集；人员覆盖只影响其对应角色/节点，不改变其他角色。未授予某动作不等于否决另一角色的有效授权；租户、账号状态等硬约束仍必须满足。

多角色合并与覆盖作用域按T-05固定，不再比较并集/交集或全局个人上限三种候选。原包“三级覆盖”不能证明人员管辖无条件覆盖全部六种范围；T-16明确人员管辖归属具体角色成员关系；空覆盖无授权，删除覆盖才恢复继承；指定部门默认不含下级。已确认的合并规则可直接形成以下预研真值表，字段能力仍绑定该对象上实际匹配的授权来源，不能从不匹配的角色借用敏感字段权限。

| 同一节点内的输入 | 应得权限 | 禁止结果 |
|---|---|---|
| A可编辑本部门，B可查看全站 | 查看全站；编辑本部门 | 编辑全站 |
| 上例中对该人员把A范围覆盖为自己 | 查看全站；编辑自己 | 覆盖同时收窄B，或从B借范围扩大编辑 |
| A可查看甲部门，B可查看乙部门 | 查看甲、乙部门允许集合 | 只取两者交集，或扩大到全站 |

以上为已确认目标语义，测试执行状态仍为未执行。可配置的显式拒绝机制不是本轮新增获批功能，不能用规则引擎自带deny选项推翻T-05。

### 3.4 团队关系与组织范围的必要样例

主管 M 主部门为甲部门；人员 A 在甲部门且直属经理是 M，B 在乙部门且直属经理是 M，C 在甲部门但直属经理是 N，D 在甲部门子部门且直属经理是 N，E 在乙部门且直属经理是 A。

| 场景 | 应包含 | 应排除 |
|---|---|---|
| M 的“我的团队” | A、B | C、D、E；E 是间接下属也不纳入 |
| M 的报表节点为“本部门数据” | 甲部门内符合其他条件的成员，包括 C | B、D、E |
| M 的报表节点为“本部门及下属部门” | 甲部门及子部门成员，包括 C、D | B、E |
| 项目允许团队管理者增删学员，M 使用团队管理能力 | A、B，并满足项目状态及其他约束 | C、D、E |

项目的“允许团队管理者添加/移除学员”开关是团队管理授权路径的必要条件。项目负责人任命能管理哪些动作须由任命能力表明确列出，不能把团队开关误用为全部角色的总开关，也不能因有报表导出权限便自动取得项目指派权限。

## 4. 对象任命、授权上限与分类权限

### 4.1 对象任命是限定对象的授权来源

中央判定先执行租户、账号、对象存在性/有效性、状态转换、发布/可学习状态等硬约束，然后合并当前动作的合法授权来源。发布状态是按动作定义的硬约束：维护草稿可以合法，学员学习未发布内容不能因被任命而自动放行。对象授权只作用于具体对象和明示能力，不能变成用户在同类资源上的全局角色。

角色权限与对象任命采用来源并集，仍须保留“授予了哪个对象的哪个动作及哪些字段”。项目负责人不因此得到其他项目、员工名册全量导出、全部敏感字段、角色管理或租户管理能力。分类创建者“目录所有权限”限定于该目录的配置动作集合，仍遵守租户与继承锁定等约束；T-16明确继承锁定约束创建者，独立课程覆盖只替换浏览权限。

T-06的入口实现：`training`维护项目负责人关系，中央authz将有效任命映射为“后台壳可进入＋培训中心对应节点/动作＋任命项目集合”。菜单、后台路由和`/auth/me`能力提示同源；不能只在学员端增加一个项目管理页面，也不能复制一个永久全局后台角色。任命动作表按已定负责人能力逐项注册，不用`training.*`通配放开所有功能。培训中心列表、搜索、分页、count、详情、修改及导出均先应用对象范围；项目内人员选择仍经受控接口，不因此开放组织人员全量查询。

| 用户授权情况 | 管理后台与功能入口 | 项目范围 |
|---|---|---|
| 仅普通学员，无任命和其他管理授权 | 无管理入口，后台业务直链拒绝 | 无管理权限 |
| 学员被任命为P项目负责人 | 可进入管理后台；开放培训中心对应节点和负责人动作 | 仅P；其他项目、未授权培训功能和其他管理模块均拒绝 |
| 同时负责P、Q，撤销P任命 | 保留管理后台及Q需要的功能 | Q保留，P的任命权限在下一请求失效 |
| 撤销最后一个任命，且无其他管理授权 | 关闭管理入口，新的后台业务请求拒绝 | 无管理权限 |
| 任命之外另有合法管理角色 | 合并该角色与任命的有效入口、动作 | 角色已授范围保留，不被任命范围反向收窄 |

此表是T-06的目标验收补充，不代表原站行为已验证。取消任命、失去对应关系、禁用用户时，在同一数据库事务中更新关系并递增权限版本；下一请求移除已撤销来源后重新判定。剩余角色或任命仍可独立授权；禁用账号则由硬约束整体拒绝。已打开的页面可保留视觉内容，但任何新查询、保存、导出和文件领取都重新验证。安全断言以服务端为准，前端可用通知刷新入口，不把刷新速度当作撤权保证。

### 4.2 1/2/3 级与“不能授予自己没有的权限”

1 级最高且不可通过普通新增接口创建；新增接口仅接受 2/3 级。2/3 级操作者不得修改同级或更高级角色。T-16授权管理必须选择managementRoleMembershipId，等级与可转授节点/动作/范围/字段都来自同一有效上下文；1级系统预置角色不经普通界面修改，不按最小等级数字或“超管”名称全量放行。

授权上限必须由服务端对拟授予项逐项验证：

`拟授予(节点, 动作, 数据集合, 字段能力) ⊆ 操作者可转授(同节点, 同动作, 数据集合, 字段能力)`。

例如操作者只可导出甲部门人员，则不能给下级角色授予“导出全部数据”；只有脱敏手机号能力，则不能转授原始手机号；只有项目 P 的负责人任命，不能据此给某角色发放全部项目编辑权限。个人拥有某能力也不必然意味着可转授，任命类权限不自动进入可转授集合。

范围比较不采用六枚举的大小排序。“指定部门”和“本部门”可能交叠但并不包含；“自己的数据”在课程节点可能不是部门范围的子集。比较应针对明确的节点、动作及业务集合语义，同时保存授权来源与上限约束。动态部门变动不能使授权扩大到授予人能力之外：authz.delegation_provenance保存来源角色成员、上限快照与版本。源授权/组织变更时同事务递增权限版本并将依赖授权标为recheck_required；中央策略拒绝尚未重验者，重验通过才active，超限suspended。依赖循环拒绝；系统种子有明确system_origin。预研须验证该传播与恢复机制，不只比较创建当天的人员集合。

### 4.3 分类的独立动作、继承锁定和扩展点

分类浏览、维护、分发、下载分别授权。浏览允许在有效学习场景中看和学；维护不推出浏览全量学员数据；分发不推出维护；下载还须满足资料可访问等前置条件，不能因为允许浏览就发 OSS 下载地址。公开分类在目标系统内解释为当前租户全员浏览，不能扩展为跨租户或互联网匿名公开；游客和分享场景仍需各自配置。

继承父分类时记录有效来源并锁定当前设置；父分类强制所有子分类继承时锁定受影响子分类。后端同样检查锁定来源，禁止通过直接 API、批量导入或并发修改绕过。T-16强制继承锁定同时限制创建者及课程独立覆盖；允许独立设置时，课程custom替换浏览集合但受所选上下文可转授上限，不增加维护/分发/下载。向父分类添加权限作为显式目标父分类授权命令，预览逐项拟追加的允许项、保留现有项；只修改已确认父级，不递归开放整棵树，仍执行锁定和转授校验。分类最多 10 层，组织最多 20 层，两套层级不可混用。

扩展使用 `SubjectResolver` 和统一授权关系：当前支持用户、角色/管理员、分类创建者等；未来加入 `classroom_admin`、`classroom_member` 只新增主体解析和成员来源。分类预留 `college_id`，当前指向主课堂；动作注册表预留扩展能力。资源查询始终消费同一 `ScopeSpec`/授权关系协议，**增加主体类型不得修改课程、列表、报表等资源查询逻辑**。预研将新增一个模拟企课堂成员主体，验证其能用既有查询命中授权课程；这只是扩展验证夹具，不提前建设企课堂产品功能。

## 5. 当前授权与历史统计分别处理

学习记录中的历史部门、岗位、状态快照用于统计归属和历史复现；当前人员表用于当前组织成员、直属经理、账号有效性及当前策略解析。不能为了让“上月数据不漂移”而让已失去管辖关系的管理员永久访问原部门人员的全部未来记录，也不能为了执行当前范围而重写历史快照。

T-15已选择当前成员模式：当前角色/组织关系决定可查人员，事实data_company_id决定所属公司，再按历史部门/岗位快照统计。一次人员调岗不能让旧主管永久保留访问权；同公司新主管可在当前许可范围查看该成员历史，历史分组仍显示原部门。跨公司调动时旧事实留在旧公司，新公司不得自动读取；需要对应公司授权的内部管理员及相应节点范围才能跨公司查询。

账号状态筛选使用当前enabled/disabled/deleted投影，历史状态仅用于复现当时事实。账务有T-15明确的本人例外：个人账户页可查看自己的各公司分账，必须逐公司显示，不自动开放旧公司的学习报表、他人资料或相互抵扣。管理账户读仍须公司上限与节点范围；不允许以SELF通用报表范围绕过历史公司边界。

节点的SELF锚点必须登记且与对象类型匹配：人员/学习/账务用person_id；课程维护用稳定uploader_id；项目配置用原创建者created_by，项目负责人任命另作授权来源；面授配置用owner_id。范围维度不同的节点不机械套用全部六范围；不支持的scope配置拒绝保存。组织事实统一经中央策略端口解析。课程共享按内容授权执行，不因内容创建者所属公司而自动共享该公司人员数据。

## 6. 列表、详情、导出、领取与字段脱敏的一致性

### 6.1 同一授权计划贯穿全部入口

| 入口 | 强制行为 |
|---|---|
| 列表、搜索、自动补全 | 先在 SQL 中限制授权数据，再排序和分页；客户端筛选只能缩小已授权集合 |
| `count`、页数、聚合、部门人数 | 与数据查询使用同一授权谓词；不能返回租户总数后只过滤本页 |
| 详情、直接 ID、批量 ID | 将对象 ID 与授权谓词一起查询；批量中部分越权不能通过返回名册或错误细节泄露对象信息 |
| 修改、指派、导入 | 对目标对象与所有被操作对象检查当前能力、范围及状态；同一事务内复核高风险写入所用版本 |
| 导出创建与执行 | 创建时验证，异步任务执行时再次验证当前身份、版本、数据范围与字段；不长期使用创建时旧快照放行 |
| 导出结果领取 | 再次验证当前能力、版本和文件范围；相关权限或范围发生变化则拒绝旧文件领取并要求按当前范围重新生成 |
| 课件下载和临时文件领取 | 检查独立下载能力、当前资源访问和状态；不得把对象存储路径或可绕过授权的长期 URL 直接返回 |

导出文件可能包含创建时的合法数据，而用户领取时已失权，因此文件存在不代表允许领取。若承诺“撤销后下一请求生效”，仅靠数分钟有效的 OSS/CDN 签名链接无法满足；需经过逐次校验权限版本的受控下载入口或边缘鉴权，存储保持私有。已下载到用户本地的字节无法追回，不把它误报成系统撤权失效；T-16采用下一新请求生效，不承诺中断全部在途输出；异步导出执行、领取及媒体每个新分片仍须重验。

### 6.2 SQL 设计验证要求

预研须实际执行 PostgreSQL 参数化查询并保存 `EXPLAIN (ANALYZE, BUFFERS)`，不是只展示 ORM 条件对象。以下是受限人员集合的查询形状示意，不是已执行 SQL。`:permitted_person_ids` 只能来自 `OrganizationPublic.resolveScopeMembers(ScopeSpec, authzRevision)` 返回且通过版本校验的服务器内部集合，不能由客户端提交。CTE 是 report 本次请求自己的许可关系，不读取 organization 私表：

```sql
WITH request_permitted_person AS (
  SELECT DISTINCT person_id
  FROM unnest(CAST(:permitted_person_ids AS uuid[])) AS allowed(person_id)
)
SELECT lr.id, lr.person_id, lr.historical_department_id, lr.source_updated_at
FROM report.learning_fact lr
JOIN request_permitted_person pp ON pp.person_id = lr.person_id
WHERE lr.tenant_id = :tenant_id
  AND lr.data_company_id = ANY(CAST(:permitted_company_ids AS uuid[]))
ORDER BY lr.source_updated_at DESC, lr.id DESC
LIMIT :page_size;
```

实际预研须把参数绑定、许可关系版本校验和本节点其余对象条件补齐为完整可运行查询，分别测六范围、多角色、对象并集、分类关系和历史模式。`ALL_TENANT` 使用租户谓词并保留其余硬约束，不生成全员数组。大集合可使用 report 自己的请求级暂存关系，按请求/租户隔离并及时清理；不能为便利直接 JOIN organization 私表。当前人员状态筛选也经拥有模块接口取得版本一致的筛选关系或验证本模块当前投影的新鲜性，先进入 SQL，不能分页后补过滤。总数查询复用相同授权关系；分页不能先取全租户前 50 条再过滤。部门闭包、直属经理、角色成员等索引分别由拥有模块维护并暴露验证结果；report 仅维护自己的事实和许可关系索引。聚合、去重及稳定排序必须在同一个授权数据集内完成。

禁止 N+1：列表不能每行调用一次规则引擎、查询一次角色或执行一次部门递归。动作授予、范围解析和字段能力应按请求/节点批量计算，资源关系在 SQL 中用 join/exists 或批量关系表表达；页大小从 20 到 200 时，授权查询次数不得线性增长。导出采用批次/游标遍历已授权集，不加载全量进程内过滤。

### 6.3 字段在服务端投影与脱敏

手机号、邮箱、身份证号权限按节点独立处理。没有原值能力时，服务端只输出脱敏值或不输出该字段；列表、详情、导出、搜索提示、错误响应、缓存、日志均不能携带隐藏的原始值让前端再遮盖。学员/主管默认没有身份证号原值权限；手机号与邮箱按已确认基线脱敏。字段权限也不能通过跨角色的粗粒度并集扩大：能在甲部门导出原始手机号，不代表可以在乙部门导出原始手机号。

### 6.4 拒绝的业务表现

前端呈现业务空状态或操作提示，例如“你暂时不能查看这项学习记录，请联系管理员确认学习报表的数据权限”，并给出安全的权限申请路径/返回学员端入口。页面不展示裸 403、堆栈、SQL、角色策略原文或目标人员姓名。

API 可以返回 HTTP 403；对象不可见场景采用一致的拒绝/不存在策略，不能用响应差异枚举对象。T-06已确认的后台入口和授权项目直链应放行，不得套用“学员所有管理URL都拒绝”；越项目、越模块或未授动作仍拒绝。权限基础设施暂不可用时可返回无业务数据的503与“服务暂不可用，请稍后重试”，这仍是拒绝授权，不是降级放行。

## 7. 权限版本、缓存与两实例撤权

为保证“撤销事务提交后发起的下一请求生效”，初版权威版本统一为02中的 `authz.tenant_authorization_revision.revision`，采用粗粒度租户修订号，先取得可证明的正确性，再考虑细分人员/节点版本优化。本文 `authzRevision` 均指该修订号。

1. 角色、角色成员、人员管辖、单人覆盖、任命、分类继承、字段授权、部门调整、直属经理调整、相关人员状态等变更，在 PostgreSQL 同一事务内递增租户权限版本，并写审计事件。对象发布状态另由权威状态读取校验，不能只在缓存中判断。
2. 每个受保护请求从权威数据库读取当前版本及账号有效性；本地 L1 和 Redis L2 仅缓存按 `tenant + user + version` 键控的不可变策略快照。不能使用本地 TTL 内旧版本直接放行。
3. 缓存缺失时，按同一版本从数据库构建快照，构建前后校验版本；中途版本变化则重试或拒绝。Redis 发布/订阅可以促使实例清缓存，但不能作为唯一撤权保证。
4. 两个应用实例不共享内存。A 实例撤销并提交后，B 实例下一请求读取新版本，旧快照即使仍存在也不能命中。测试必须故意丢弃 Pub/Sub 消息，验证撤权仍成立。
5. **Redis 故障采用 fail closed**：连接失败、超时、版本快照无法可靠取得时，不使用本地旧快照授权，不为提高可用性跳过检查，返回无数据的暂不可用提示。允许重新设计有证明的数据库降级路径，但必须单独评审，不能在故障处理中临时加入。
6. 权威数据库不可读、版本不一致或策略无法解析同样拒绝；未知角色/节点/主体不能默认为有权限。恢复后只接受当前版本快照。
7. 高风险写入需要在提交前复核权限版本与关键对象状态，避免请求校验后、提交前被撤权的竞态。跨长任务在执行和每个输出阶段重验；需要保护版本变更和业务提交的事务排序，预研验证其锁和死锁影响。

这里的“立即”有明确线性化边界：撤销事务提交后**新发起的请求**必须使用新权限。已经开始且已发送的数据不能撤回。T-16已确认不要求撤销瞬间中断全部在途读取，若未来增加该保证须另评输出门禁与流中断，不能改写现有证据。

## 8. 原生 PolicyService 与 Casbin 的预研比较

| 能力 | 推荐的业务归属 | Casbin 候选可能承载的部分 | 仍需本项目设计和验证 |
|---|---|---|---|
| 租户、节点、动作的规则匹配 | 中央 authz | 基础匹配、角色关系、domain/policy adapter | 当前账号/对象硬约束、导航例外、生命周期 |
| 多角色与人员覆盖 | T-05已定角色内先覆盖，再按节点/动作合并有效授权 | 执行已选并集语义 | 校验不串用动作/范围；规则引擎deny能力不能改变已定合并规则 |
| 六范围与人员管辖 | 业务 ScopeSpec | 可引用范围标识或自定义函数 | 范围解析、节点锚点、动态集合比较、SQL 编译 |
| 分类继承与锁定 | 分类域 + authz | 原子关系匹配 | 生效来源、父子锁定、课程覆盖、冲突处理 |
| 对象任命、角色等级 | 任命域/角色域 + authz | 有界关系查验 | 对象能力表、可转授边界、状态约束 |
| 列表/count/导出一致 | 仓储 + PolicyCompiler | 不能仅靠单对象 enforce 代替 | 批量数据过滤、真实 SQL、字段投影、分页安全 |
| 撤权与多实例 | authz 版本协议 | adapter/watcher 等辅助机制 | DB 权威版本、失效时序、故障关闭、竞态 |

预研优先以小型 Native `PolicyService + ScopeSpec` 骨架证明业务契约能表达需求，再以同一夹具接入 Casbin 候选，比较其减少了多少维护成本、增加多少复杂度。不得为了适应引擎而把三级覆盖删掉、把六范围简化成三个角色、把 SQL 过滤退回逐对象调用，或将业务未决问题伪装成“技术框架不支持”。

### 9.5 启动前冻结的性能指标（实际结果见12）

建议先固定一份基准：PostgreSQL 4 vCPU/8 GB、每个应用实例 2 vCPU/4 GB、两个应用实例、独立 Redis，同地域网络；记录实际机器、数据库参数与软件版本。如果实际环境不同，须先修订基准，不能跨环境直接比较。

拟测 50 个并发客户端、每页 50 条、持续 10 分钟并记录预热/冷启动分段；读请求涵盖简单及最复杂范围。建议候选目标：权限判定额外耗时 p95 ≤ 50 ms，含过滤和 count 的普通列表端到端 p95 ≤ 500 ms；复杂历史聚合单列报告，建议 p95 ≤ 2 s；错误率与授权错误数分别报告，授权错误必须为 0。冷热缓存和 Redis 故障需要分开测，不把失败请求快速返回计入正常请求延迟。

授权查询次数须与页大小解耦，20/50/200 条分页不能引入逐行鉴权查询；缓存与索引优化不能牺牲撤销时效。以上是评审用性能目标，不是已经测得的结果或生产 SLA。未达目标需定位 SQL/索引/协议成本并重测；若三天结束仍未解决，则 No-Go，明确延期或调整方案，不忽略性能门禁。

### 9.6 Go / No-Go

**Go 必须同时满足**：本期必需业务语义经确认；测试真值表通过；租户隔离、授权上限、字段保护、分页/count/导出一致和撤权测试零失败；真实 SQL/执行计划可复现；无 N+1；两实例和 Redis 故障测试通过；性能达到评审后的指标；维护边界清晰且 B1-05、B1-07、B1-08 分项重新估算。

Casbin 未通过而 Native 原型通过，不自动视为整个预研失败，也不自动允许立刻开工：应记录 Casbin 不适配的具体能力、选择集中自研 PolicyService，并按新增业务代码和测试量重新估算，经方案复核后再过门禁。若 Native 也不通过，或失败原因是业务语义未裁定，则暂停依赖权限底座的正式开发，补充设计/澄清后复测。**不能以“框架不好用，先写业务以后补权限”替代门禁。**
