## 0. 只读分析得到的关键事实

1. **历史聚合 SQL**（`src/report/service.ts:22-71`）。授权只作用于（tenant, person_id, data_company_id）和人员当前状态（`report.person_projection` 中的 enabled/deleted），不按单条事实授权。history 节点不绑定原值字段（`src/authz/registry.ts:5`，`rawFields: []`）。
   - 宽历史（actor M，单来源 `all`、无配对）走旧 JOIN 路径，SQL 指纹 75b191b0575a，扫描 100 万条事实。
   - 复杂历史（person-00003）走 MATERIALIZED 关系前置路径，SQL 指纹 7f276423032a，返回 457,673 条事实。
2. **合成数据的形状**（`sql/seed.sql:15`）：每人约 20 条事实；每条事实的历史部门（i%20）、岗位（i%5）、状态（i%7）几乎互不相同。**结论：按"人"粒度预聚合几乎不压缩行数**（约 100 万事实对应约 100 万个人粒度分组键），只把明细换成同等规模的汇总表，不能对准根因。
3. **事实变化不推进 `authz.revision`**（版本触发器只挂在组织/授权类表上，`scripts/seed.ts:33-34`）。所以 T-1 预聚合的刷新与撤权版本互不牵连，撤权实时性不受预聚合影响。
4. **连接池**（`src/infrastructure/db.ts:9`）：每个 API 一个全局池（max 20，获取超时 800ms，SQL 超时 10s）。权限读、业务读、事务和导出锁共用这一个池，每条 `pool.query` 单独获取一次连接。
5. **每请求的权威读取**（热缓存）：token 1 次；`authority.current` 被调用 3 次（加载、加载栅栏、计划栅栏，`src/authz/revision.ts:95,116,152`），每次 3 条语句，共 9 次；`scope.resolve` 0～2 次。热缓存下总查询数为：宽历史 11、复杂历史 13（`test/native-history-relation.test.ts:165` 已断言为 13）、两类列表各 14。
6. **T-16 的实现方式**：每个请求都从 PG 重读 `authz.revision`、公司授权和人员状态；栅栏发现版本变化即返回 503；快照键包含 revision；Redis 每请求做实时 PING，出错一律拒绝；DB 出错一律 503。无 Pub/Sub。

## 1. 整改项 1：历史聚合改走 T-1 预聚合（优先）

**口径**：只把"历史事实"冻结到 T-1；授权、人员当前状态、公司上限、来源配对仍然实时计算。理由见第 4 节的待确认项。

**设计：按"格子"预聚合，再按授权覆盖度组合**

- 新增投影表 `report.history_cell_agg`，键为（tenant, 刷新批次, data_company_id, 刷新时人员的当前部门, 历史部门, 历史岗位, 历史状态, fixture），值为 count 和 sum(points)。另有一张人员粒度的补差表 `report.history_person_agg`，结构相同，只是把"部门"换成 person_id。
- 每日 T-1 刷新：在一个事务内重建两张表，并写入批次表 `report.history_agg_batch(batch_id, as_of, 状态)`；查询只读已完成的最新批次。
- 查询时：
  1. 照原样得到授权人员集合 S。原 `scope.resolve` 和编译器结果不变，公司上限、来源配对同样作用到（人员, 公司）。
  2. 对每个（部门, 公司）格子：如果格子在刷新时的全部成员都在 S 里（且配对允许），并且这些成员自刷新以来没有调岗、移籍或状态变化，就整格读 `history_cell_agg`。
  3. 其余人员（部分覆盖的格子、刷新后发生变化的人员）读 `history_person_agg` 补差。
  4. 人员当前状态（enabled/deleted）仍按实时 `person_projection` 过滤。
- 接口在顶层新增 `dataAsOf`（批次的 as_of）和 `historyMode: "T-1"`，页面可据此标注"历史统计截至 T-1"。不加在行内，原 count/rows 摘要的校验不受影响。实时列表接口 `/report` 的口径不变。

**正确性要求**：同一批次下，预聚合结果必须与"在刷新时刻的事实集合上用原 SQL 实时计算"的结果逐组一致（count、points、分组集合），由独立真值核对。基准负载的事实在测量期间不变，所以 T-1 结果应与现有独立真值完全一致。

**风险**：如果真实授权集合高度碎片化（大量格子只被部分覆盖），收益会退化为人员粒度扫描。合成负载中，复杂身份的范围是"部门段 × 公司 I/A"，大部分格子会被整格覆盖，但这只能说明本负载，报告中会写明。

**需要改的测试**：`native-history-relation.test.ts` 中对 CTE 物理计划、SQL 形状和查询数的断言。只改与 SQL 形状有关的断言；语义断言一律不改。

## 2. 整改项 2：分析查询与权限/事务查询隔离（优先）

**设计**：在每个 API 进程内把单一池拆成三个池，总连接数仍为 20，不增加资源：

| 池 | 连接数（初值，待按基线调整） | 用途 |
|---|---:|---|
| authz | 8 | token、权威读取、栅栏、scope.resolve、快照构建 |
| tx | 4 | 事务写入、导出锁 |
| analytics | 8 | 报表、历史聚合、导出数据读取 |

- 获取超时（800ms）和 SQL 超时（10s）在三个池中都保持原值，不放宽。
- 理由：归因显示，列表和权限的 p95 主要花在 `pool.acquire@authority.current` 上，原因是 7～11 秒的历史 SQL 长时间占住共享池。分池以后，权限读不再排在重型分析查询后面。PG 侧仍是同一个实例（4 CPU 不变），CPU 争用不会因分池消失，所以分池要和整改项 1 一起才能见效。
- 不选只读副本：会增加资源，并引入复制延迟，可能影响 T-16 的"下一请求"语义。
- 导出事务目前持有 `authz.revision` 的 FOR UPDATE 锁，同时在锁内跑历史聚合（`src/infrastructure/protected-exports.ts:13,21`）。整改后锁内只读 T-1 预聚合，持锁时间会缩短。这里的锁序不改。

## 3. 整改项 3：合并每请求多次权威读取（前提：T-16 语义不变）

**设计**（不减少栅栏的次数，只减少每次栅栏的往返）：

1. `authority.current` 的 3 条语句（revision 和公司授权、人员行、revision 复读）合并为 1 条语句，在同一快照内读出。原先第 3 条"复读 revision 防止前两条之间变化"的作用，由单语句快照天然保证。
2. token 查询并入第一次 `authority.current`，按 token_hash 联查 session、revision、授权和人员。
3. 加载栅栏和计划栅栏仍然保留，各自都是从 PG 读取的单条实时语句。版本变化时仍返回 503，原 `races.test.ts` 中"快照构建跨越撤权返回 503"的行为不变。
4. `scope.resolve` 的 2 条查询（部门树、人员）合并为 1 条。

**预期**：热缓存下权限往返从 10～12 次降到 3～4 次（估算）。

**作废条件**：任何一个 T-16 场景结果变化，本项作废、整体回退，不调整 T-16。需要核对的是：选定回归 55 项及 456 条字面观察、10 个故障阶段 × 16 条路径、下一请求时序 9 项，外加不在回归脚本里的 `races.test.ts`、`task4-review-regressions.test.ts:80`、`http.test.ts`、`telemetry-http.test.ts`。
