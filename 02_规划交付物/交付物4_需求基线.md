# 一、组织与账号（ORG）

## REQ-ORG-01 组织树
- **业务目的**：为指派范围与统计维度提供组织基础。
- **规则**【原站已验证 E005】：
  - 组织为**多级树**，节点含 ID、名称、父节点、层级。
  - 节点显示**人数计数**。
  - 📘 **部门层级最多 20 级**（手册·常见问题1）。
- **输入**：组织名称、父节点。**输出**：组织树、各节点人数。
- **权限**：仅管理员可增删改；主管与学员只读且受数据范围限制。
- **依赖**：无。
- **验收条件**：
  1. 能创建至少三级组织，层级展示为 `一级->二级->三级` 路径格式。
  2. 节点人数口径须与 REQ-RPT-05 一致（仅主部门、是否含子部门可选）。

## REQ-ORG-02 人员档案
- **业务目的**：人是学习的主体，也是权限与统计的载体。
- **规则**【原站已验证 E003/E005】：
  - **账号是稳定身份**，创建后不可修改，个人端只读。
  - **工号与账号分离**，工号可为空。
  - 人员归属 **1 个主部门**；兼职部门字段预留（V1 不启用）。
  - **直属经理**为人员引用字段，**是主管数据范围的唯一来源**，不从组织树推导。
  - **入职时间**必须可维护（指派规则维度之一）。
  - 状态：**启用 / 禁用 / 删除（软删除）**。
- **输入**：姓名、账号、工号、手机号、邮箱、主部门、岗位、直属经理、入职时间。
- **输出**：人员列表（支持按上述字段筛选）、人员详情。
- **权限**：管理员可增删改；主管只读本团队；学员只读本人且仅手机/邮箱可自助绑定。
- **依赖**：REQ-ORG-01。
- **验收条件**：
  1. 创建人员后账号字段变为只读，任何角色均无法修改。
  2. 禁用人员后，该人员无法登录，但**其历史学习记录仍完整保留且可查询**。
  3. 删除人员为软删除，可恢复；恢复后其历史学习记录仍在。

## REQ-ORG-03 人员状态与记录保留【新增-明确化】
- **业务目的**：保证历史报表可复现。
- **规则**：
  - 【原站已验证 E007 §2】原站数据大屏**硬性排除**禁用/删除人员；报表中心**可筛选**（启用/禁用/删除，默认启用）。
  - 【有意差异】V1 规定：**学习记录中存储人员的部门/岗位/状态快照**（记录写入时点的值），而非实时关联。
  - **理由**：原站此点未验证（V-35）。存快照可保证"上月报表下月再看数值不变"，避免人员调岗或禁用后历史数据漂移。
- **验收条件**：
  1. 学员 A 在 X 部门完成课程 → A 调岗到 Y 部门 → 重新查询上月报表，A 仍计入 X 部门。
  2. 学员 A 被禁用 → 默认报表不含 A；将人员状态筛选改为"禁用"后能查到 A 的历史记录。

# 二、角色与权限（ROLE）

## REQ-ROLE-01 三维权限模型
- **业务目的**：权限是平台可信运营的底座。
- **规则**【原站已验证 E006 §1】：
  权限定义为三元组：`角色 × 功能节点 → { 导航可见性, 操作权限集, 数据范围 }`
  - **导航**：该节点菜单是否可见（布尔）
  - **操作权限**：节点内可执行操作的集合（多值）
  - **数据范围**：**按节点单独配置**，非角色级一刀切
- **验收条件**：
  1. 同一角色在"课程管理"与"学习报表"两个节点上可配置不同的数据范围，且互不影响。
  2. 关闭某节点的导航权限后，该角色菜单中不出现该项，**且直接访问其 URL 也被拒绝**。

## REQ-ROLE-02 权限的两个来源
- **规则**：
  - 【原站已验证 E010 §8】权限 = **角色权限 ∪ 对象级任命**。
  - 对象级任命包括：项目负责人、课程贡献者/上传者、分类创建者（「创建人有该目录的所有权限」）、团队负责人。
- **验收条件**：
  1. 一个仅有"学员"角色的人，被任命为某项目负责人后，能管理该项目（且仅该项目）。
  2. 取消任命后立即失去该项目的管理能力。

## REQ-ROLE-03 V1 三角色定义
- **规则**：

| 角色 | 导航 | 操作 | 数据范围 |
|---|---|---|---|
| **管理员** | 全部管理端菜单 | 全部 | 全租户 |
| **主管** | 我的团队、团队报表 | 查看、导出；**可在项目中添加/移除本团队学员**（受项目开关控制，E010 §8） | **「本部门及下属部门数据」**（6 个预置范围之一，🟢 E018 §1 双证）；人员归属以**直属经理**字段判定 |
| **学员** | **管理端 0 项** | 无 | 仅本人 |

- **【原站已验证 E006 §4.1】学员在管理端 441 个权限项中勾选 0 项** → V1 直接采用此基线。
- **验收条件**：
  1. 学员登录后**看不到任何管理端入口**，直接访问管理端 URL 返回明确的无权限提示。
  2. 主管只能看到直属下属的数据，访问非下属数据被拒绝。

## REQ-ROLE-04 权限拒绝的表现【原站已验证 E008 §2】
- **规则**：拒绝时**不使用 403 错误页**，而在页面内展示友好空状态，**并给出具体的开通路径指引**。
  - 原站原文示例：「暂无权限查看课堂数据，请联系管理员开通权限　开通路径：管理端–在线课堂–企课堂–编辑企课堂」
- **验收条件**：越权访问任一受限页面，页面显示业务语言的提示 + 可执行的补救路径，不出现技术错误码。

## REQ-ROLE-05 敏感字段级权限【原站已验证 E006 §5】（V1 预留）
- **规则**：`身份证号`、`邮箱`、`手机` 在**每个含个人维度的报表上都是独立权限项**。能看报表 ≠ 能看这些字段。
- **V1 处理**：数据模型预留字段级权限位；界面上手机/邮箱默认对主管**脱敏**展示。
- **验收条件**：主管查看团队报表时，手机号显示为 `138****1234` 形式。

## REQ-ROLE-06 🆕 角色等级与授权上限约束
- **业务目的**：防止管理员越级提权。
- **规则**📘（手册·我的企业·创建角色）：
  - 新建角色**只能选择 2 级或 3 级**（1 级为系统预置，不可新建）。
  - **2 级角色不能修改同等及更高等级角色的权限**。
  - **3 级角色同样不能修改同等及更高等级角色的权限**。
  - **设置权限时，只能在自己已有的权限范围内选择**（不能授予自己没有的权限）。
- 🔵 **网页佐证**：实测 1 级角色仅「平台管理员」「运营负责人」两个，符合"1 级不可新建"。
- **验收条件**（AC-P-07🆕）：
  1. 以 2 级角色管理员身份，尝试编辑另一个 2 级角色的权限 → 被拒绝。
  2. 以 2 级角色管理员身份创建 3 级角色时，权限勾选项中**不出现自己没有的权限**。

## REQ-ROLE-07 🆕 数据权限的六个预置范围与三级覆盖
- **业务目的**：数据范围是主管与分级管理员的核心约束。
- **规则**🟢 **双证**（手册原文 + 网页下拉实测完全一致）：
  数据权限**从 6 个预置范围中选择**，不是自由配置：

  | 范围 | 含义 |
  |---|---|
  | **全部数据** | 全租户 |
  | **本部门及下属部门数据** | 本部门 + 所有子部门（**主管"多级下属"的实现方式**） |
  | **本部门数据** | 仅本部门，不含子部门 |
  | **指定部门数据** | 手工指定若干部门 |
  | **管辖范围内的数据** | 按人员级"管辖范围"设定 |
  | **自己的数据** | 仅本人 |

- **三级覆盖**🟢：
  1. **角色级**：为角色在某功能节点上设定范围
  2. **人员级**：在角色人员管理中，为每个人单独设置「管辖范围」
  3. **单人覆盖**：「添加授权人员」可对角色下的**部分人员设置独立的数据权限范围**
- 🔵 **网页补充**：不同功能节点的数据权限**可配维度不同**（如积分商城节点为商品范围/人员选择范围/商品分类范围），由该节点业务决定。
- **依赖**：REQ-ORG-01（组织树）、REQ-ROLE-01（三维模型）。
- **验收条件**：
  1. 主管角色在"个人学习详情"节点设为「本部门及下属部门数据」→ 能看到本部门及所有子部门学员，看不到平级部门。
  2. 同一角色在"课程管理"设「全部数据」、在"学习报表"设「本部门数据」→ 两者互不影响。
  3. 对角色下的某一人单独设为「自己的数据」→ 该人只能看到本人数据，同角色其他人不受影响。

# 三、课程分类与可见范围（CAT）

## REQ-CAT-01 分类树与权限矩阵
- **业务目的**：可见范围的根。
- **规则**【原站已验证 E016 §3】：
  - 分类为多级树，含课程计数。📘 **分类层级最多 10 级，分类名称 ≤50 字**。
  - 权限矩阵：**主体**（管理员&创建者 / 指定用户）× **动作**（**浏览 / 维护 / 分发**）
  - **【D-32 决策】** 当前实现**两层**（分类权限 + 课程级覆盖），放弃"课堂管理员/课堂成员"两类主体与"App缓存课件"动作，保留"允许下载课件"。
  - ⚠️ **必须保留恢复为四层的可能（D-32，与 D-31 联动）**，具体预留要求：
    1. **权限主体设计为可扩展的枚举**，而非硬编码三类 —— 后续可增加"课堂管理员/课堂成员"
    2. **权限动作设计为可扩展的集合** —— 后续可增加"App缓存课件"
    3. **分类对象预留 `所属企课堂` 外键**（即使当前恒为"主课堂"）
    4. **可见性判定逻辑抽象为独立的策略函数**，而非散落在查询条件里 —— 后续增加企课堂层时只改该函数
  - **验收**：以上四项在代码评审中逐项核对；增加一个新的权限主体类型**不需要改动查询逻辑**。
  - 「创建人有该目录的所有权限」。
  - **设为公开**：对全平台开放浏览权限，**级联子分类**。
- **继承规则**【原站已验证】：
  - `继承父分类权限` → 使用父分类权限覆盖当前，**当前不可修改**
  - `所有子分类继承当前分类权限` → 覆盖所有子分类，**子分类不可修改**
- **验收条件**：
  1. 分类 A 设为公开 → 其子分类 A1 自动变为公开。
  2. 分类 B 勾选"继承父分类权限"后，B 的权限设置项变为只读。
  3. 用户仅有"浏览"权限时，能看到课程但不能编辑，也不能把课程指派给他人。

## REQ-CAT-02 三种权限动作的语义
- **规则**【原站已验证】：
  - **浏览**：能看、能学
  - **维护**：能编辑课程内容
  - **分发**：能把课程加入项目指派给他人
- **【新增-明确化】** 三者互相独立，可任意组合。
- **验收条件**：授予"分发"但不授予"维护"的用户，能把课程加入项目，但打开课程编辑页被拒绝。

# 四、课程（CRS）

## REQ-CRS-01 课程创建与编辑
- **规则**：
  - 必填：**名称（≤200字）**、**分类**。
  - 可选：封面、简介（≤2000字）、标签、编码、版本。
  - **标签**：✅ **D-26 决策：保持自由文本输入（回车即创建），与原站一致。**
    - ⚠️ **已知并接受的风险**：结合「完课自动获得关联标签」（会写入人员属性），同义标签（如"安全生产"/"安全生产培训"）会导致**后期按标签筛人不准**。
    - **缓解要求（必做）**：标签输入时**提示已存在的相似标签**供选择，并提供**标签合并**的管理功能（不阻断自由输入，但给管理员事后治理手段）。
  - **【有意差异 DIFF-10】** 创建与编辑**必须是不同路由**，编辑路由以课程 ID 为准并显示"编辑课程"标题；分步表单必须显式区分「保存草稿」与「下一步」；提交需幂等保护。
    - **理由**：原站 `/kng/#/operator/course` 永远是创建语义且预填上次草稿，"下一步"隐式创建，调研中因此产生了重复课程。
- **权限**：需该分类的"维护"权限。
- **验收条件**：
  1. 名称或分类为空时无法提交，且错误提示指向具体字段。
  2. **连续两次进入创建流程再退出，不产生任何课程记录。**
  3. 编辑已有课程并保存，课程 ID 不变，不产生新记录。

## REQ-CRS-02 课程内容与任务
- **规则**【原站已验证 E008 §4】：
  - 课程 = **任务容器**。V1 支持两种任务类型：**文档、视频**。
  - 任务字段：类型、名称、**时长**、**学分**、**必修属性**、**是否计入完成度**。
  - 📘 **必修属性有三个取值**：`必修` / `选修` / `动态调整`（依测评结果自动切换，需人才发展模块）。**V1 只实现前两个，枚举值需预留第三个**。
  - **【核心】** 「是否必修」与「是否计入完成度」是**两个独立属性**，严禁合并为单一开关。
    - 原站原文佐证：「…不参与闯关解锁…**不影响该任务是否必修及是否计入项目完成度**」
  - V1 只做**无章节**结构与**自由学习模式**（不做闯关）。
- **验收条件**：
  1. 可配置一个"必修但不计入完成度"的任务，且完成率计算时该任务被排除。
  2. 可配置一个"选修但计入完成度"的任务。

## REQ-CRS-03 课程学分
- **规则**【原站已验证 E015 §3，实测 1.9min→0.19学分】：
  - **课程标准学分 = max( 标准时长(分钟) × 系数, 保底值 )**，系数与保底值均为**平台级配置项**，实测默认 **系数 0.1、保底 0.1**。
  - ⭐ **保底值是必需的**：实测多条 `0分0秒` 的文档类课件学分均为 **0.1**（E017 复查，8 个样本）。若无保底，零时长内容会算出 0 学分。
  - 课程标准时长 = 其任务时长之和。
  - ⚠️ **v8.2 修订（技术方案审查 T-10 引出）**：本条原写作**课程级**计算，但下方验收条件 2 又要求**按任务发放**——
    **按任务发放就必须按任务计算**，这是我原文的内部矛盾。技术方案 T-10 已改为
    **逐任务 `round_half_up(max(任务时长分钟 × 系数, 保底), 2)`，课程总额 = 各任务已舍入金额之和**（不在总课时上再做一次保底）。

## REQ-INC-03 ⭐ 任务类型决定奖励触发语义【原站已验证 E023 §3.5】
- **原站把触发条件做在「任务类型」这一层，不是每个任务单独勾选。** 这是很重要的简化——管理员选了类型就自动获得正确语义。
- **两类触发**：
  | 类别 | 任务类型 | 触发文案（原文） |
  |---|---|---|
  | **「完成」即触发** | 考勤 / 投票 / 文档 / 面授 / 调查 | `考勤完成获取` `投票完成后获取` `知识学习完成后获取` `面授课完成获取` `调查完成后获取` |
  | **须达「合格/通过」** | 活动 / 作业 / 考试 | `活动合格获取` `作业合格获取` `考试通过获取` |
- ⭐ **双档奖励**：`作业` 有 `作业合格` + **`精华作业`** 两档；`考试` 有 `考试通过` + **`考试优秀`** 两档。
- **与 DIFF-21 的关系**：用户已决策"含考试的项目，完成以通过为准"——原站的做法**与该决策同向**，且更彻底：把"完成 vs 合格"的区分提升为**类型级默认语义**。**建议复刻这个做法。**
- **V1 范围**：实现 Path A 涉及的类型（文档 / 面授 / 考勤 / 活动 / 作业）。`考试`/`调查`/`投票`/`鉴定` 在需求池。
- **V1 必须预留**：双档奖励的数据结构（`基础档` + `优秀档`），即使 V1 只用基础档。
- **验收**：① 文档任务学完即发学分；② 作业任务提交但未评为合格 → **不发**；评为合格 → 发。

## REQ-INC-04 🆕 系统预计算并展示奖励上限【原站已验证 E023 §3.2】
- **原站原文**：> **「当前设置下，本项目学员有机会获取 340 学分 355 积分」**
- **规划要求**：管理员配置奖励时，页面实时汇总**整个项目的奖励天花板**。
- **为什么值得做**：这是防止学分通胀的**唯一低成本手段**。没有它，管理员配到第 30 个任务时已经不知道总量了。
- **验收**：改任意任务的学分值 → 顶部汇总数字实时变化。

## REQ-INC-05 🆕 扣减规则：系统预置 4 条，只配额度【原站已验证 E023 §3.6】
- **原站的 4 条固定规则**（名称与触发条件**不可自定义**，管理员**只能配扣减数值**，配 0 即不扣）：
  | 规则 | 触发条件（原文） |
  |---|---|
  | 学习项目未按时完成 | 员工参与项目，未在项目计划完成时间内完成 |
  | 考试未通过 | 员工参与的考试，在任务计划完成时间到期后未通过 |
  | 作业未合格 | 员工参与的作业，在任务计划完成时间到期后未合格 |
  | 鉴定未合格 | 员工参与的鉴定，在任务计划完成时间到期后未合格 |
- ⭐ **这种克制值得复刻**：不提供自定义规则引擎，避免复杂度爆炸；所有扣减统一锚定在**「计划完成时间到期」**这一个时间点上。
- ⭐ **结算时机：次日凌晨 2 点批处理**（原文「次日凌晨2点开始自动更新」）→ 见全局约束的时效分层。
- **V1 范围**：实现 `学习项目未按时完成` 与 `作业未合格` 两条（Path A 有作业）。其余两条随考试/鉴定进需求池，**但 4 条规则的配置表结构 V1 就建全**。
- **验收**：项目逾期未完成且扣减配置为 5 学分 → 次日 02:00 后该学员学分减 5，且学习记录留有扣减流水。

## REQ-INC-06 🆕 学分流水必须可追溯到来源【D-42(c) 的硬前提】
- **规则**：每一笔学分的发放与追回都必须记录：**来源层级**（任务/阶段/项目/评优/带教）、**来源对象 ID**、**发生时间**、**原因**。
- **为什么是硬前提**：D-42(c) 规定"学分对应的必修任务被删除或替换时追回"。**若流水只有总额没有来源，就无从判断该追回哪一笔，该决策直接无法实现。**
- **验收**：学员完成 3 个任务 + 1 个阶段 → 学分明细显示 **4 笔独立流水**，各自可点进对应来源对象。
- **依据**：D-42、AC-N-10、AC-E-24。

# 五c、大纲变更的重算语义（CHG）✅ **D-42 已决策**

> **来源**：原 V-37 → 永久缺口 G-05 → DIFF-33 → **D-42 定稿**。
> ⚠️ **本域全部规则为决策与推导，不是原站实测行为**（原站无已发布项目、无学员进度，无法观察）。
> 若后续获得原站实证与此不符，**以原站为准并同步修订**。

## REQ-CHG-01 新增必修任务：状态回退 + 分母重算 + 学员提醒
- **规则**【D-42(a)(b)】：
  1. 已判定 `已完成` 的学员**回退为 `学习中`**；
  2. 完成度**分母立即重算**；
  3. ⭐ **被回退的学员必须收到提醒**，内容三要素缺一不可：**哪个项目** / **为什么变** / **还差什么**。
- **为什么要提醒**：状态无声回退是最容易引发信任崩塌的一类变更。学员看到自己"完成"变回"学习中"，若无解释，第一反应是系统出错。
- ⚠️ **触达受限（承接 D-37 的已声明风险）**：本期无飞书/钉钉，**提醒只能走站内消息，触达率低**。
  → **这不是本需求的缺陷，是 D-37 的代价在此处的具体体现。** 需在验收报告中如实声明：*回退提醒已实现，但触达能力受限。*
- **验收**：AC-E-23。

## REQ-CHG-02 已发学分不追回，**但任务被删除或替换时追回该任务学分**
- **规则**【D-42(c)】：
  | 变更类型 | 已发学分处置 |
  |---|---|
  | 新增任务 | **不追回** |
  | 修改任务学分数值 | **不追回**（已发即既得，按发放时的值） |
  | 改名 / 调顺序 / 改时间窗 / 改必修属性 | **不追回** |
  | ⭐ **删除任务** | **追回该任务的任务级学分** |
  | ⭐ **替换任务** | 同上 |
- **「删除 / 替换」的判定锚点**（**这是我的操作化定义，不是原站规则**）：
  - **以任务 ID 是否延续为准**——
    - 任务 ID 消失 = **删除**
    - 任务 ID 保留但**承载内容 ID 变化**（如由课程 A 改挂课程 B）= **替换**
    - 其余一律不算
- **只追回任务级，不追回阶段级/项目级**：删除任务使完成**更容易**，阶段与项目的完成判定依然成立，追回没有道理。
- **追回下限**：学分**不得为负**。V1 学分不可消费，风险低；若余额不足，差额记为"待抵扣"，**不产生负数余额**。
  > ⚠️ 这是我的取值，**你未就此表态**。V2 引入积分商城后此规则需重审。
- **验收**：AC-E-24、AC-E-26。

## REQ-CHG-03 🆕 变更是双向的：删除必修任务可能使学员"正向"完成
- **规则**：删除必修任务后，若某学员的剩余必修已全部完成，则**状态前进为 `已完成`**，**补发**阶段级/项目级学分，并发送**完成提醒**。
- **为什么必须做**：大纲变更是双向的。只做回退不做正向补发，会沉淀一批"实际已完成但系统显示学习中"的学员，**且永远不会自愈**。
- ⚠️ **这一条你未提及，是我基于 D-42 的对称性补的。** 若不认可，删除本条即可，但需在验收报告中声明该情形不处理。
- **验收**：AC-E-25。

## REQ-CHG-04 管理员侧的变更影响提示【D-42 配套，已同意】
- **规则**：点「生效」时**必须弹窗告知影响范围**，且**管理员可取消**。
- **文案要求**：给出**具体数字**，不得只说"本次变更将影响学员"。
  例：「本次变更将影响 **152 名学员**，其中 **37 人的完成状态将回退**，**12 人将被追回合计 120 学分**」。
- **验收**：AC-E-23（含"管理员可取消"分支）。

## REQ-STU-03 学习进度记录
- **规则**：
  - 【原站已验证 E015 §7.2】**完成条件 = 累计观看时长达到内容总时长**（非"播放到最后一帧"，非"打开即完成"）。
  - 【原站已验证 E015 §7.3】进度为**节流上报**，实测约 20 秒一次。
  - **【新增】V1 必须在页面卸载时补报进度**（`beforeunload`/`visibilitychange`）。
    - **理由**：实测原站进度上报滞后达 16 秒，学员在两次上报之间关页面会丢失该段学习。原站是否有补报未验证（V-46）。
  - 📘 **拖拽的精确规则（v2.0 修订）**：禁止拖拽开启后，视频/音频类内容**仅在首次学习完课前不可拖拽；完课后重复学习不限制拖拽**。V1 **默认开启禁止拖拽**。
  - 📘 **防挂机（⚠️ D-25 后升级为必做）**：两种模式——① 检测疑似挂机弹窗确认，未确认则停止播放；② 需在 N 秒内确认，**未确认则本次学习无效，进度回退到本次开始前，且不获得学时与学分**。
  - 📘 **防多内容同时学习（⚠️ D-25 后升级为必做）**：同一时间只能学习一个内容，否则提示。
    - **理由（重要）**：D-25 决定「倍速计时长默认开启」，与 DIFF-26（学习时长无上限）叠加后**刷时长的风险显著上升**。
      原站是靠 **倍速计时长 + 防挂机 + 禁止拖拽 + 防多内容同时学习** 这一整套**组合**来平衡的。
      **只复刻倍速而不复刻防刷三件套，会得到一个比原站更容易被刷的系统。** 因此这两项由"建议"升为**必做**。
- **验收条件**：
  1. 学员观看 30 秒后直接关闭浏览器标签 → 重新打开时进度不小于 30 秒对应的百分比。
  2. 课程未开启拖拽 → 进度条不可拖动。
  3. 学员观看满全部时长 → 状态变为"已完成学习"。

## REQ-REC-02 进度与时长是两条独立链路【原站已验证 E015 §7.6 + E017 §3】

- ⭐ **v8.0 修订：时效分层是五层，不是四层**【E023 §3.6 补证】

## REQ-REC-04 🆕 学习时长必须是两个字段（V-48 结案后新增）
- **规则**【原站已验证 E017 V-48 结案，实测 有效 1.92 / 累计 3.82】：

  | 字段 | 定义 | 用途 |
  |---|---|---|
  | **有效学习时长** | **min(累计有效观看时间, 内容标准时长)** —— **封顶** | **学分换算、考核、合规上报** |
  | **累计学习时长** | 全部学习行为时间累加 —— **无封顶** | 反映投入程度、活跃度分析 |

- **实证**：完整观看 115 秒（1.917 分钟）的课件后，有效学习时长 = **1.92 min**（精确吻合内容时长），累计学习时长 = **3.82 min**（含多次打开页面的时间）。
- ⚠️ **这修正了 DIFF-26 的判断**：原站**并非没有防刷设计**，「有效学习时长」就是封顶机制。此前"需新增单课程时长封顶规则"的建议**作废**。
- **学分按有效学习时长换算**，不按累计（解释了 REQ-CRS-03 中学分与内容时长精确对应的现象）。
- **验收条件**：学员重复学习同一课程 3 次 → **有效学习时长不超过内容标准时长**，**累计学习时长为三次之和**；获得学分**不重复发放**。

## REQ-REC-05 🆕 学员端与报表端的时长口径必须一致（DIFF-32）
- **原站缺陷**【E017 V-48 实证】：同一条学习记录，**学员端显示「学习0分钟」，报表端显示「有效 1.92 / 累计 3.82 分钟」**。
- **问题**：学员看到"学了 0 分钟"会误以为学习未被记录，可能重复学习或投诉。
- **V1 要求**：学员端与报表端**取同一字段、同一口径**；学员端若展示时长，**必须明确是「有效学习时长」**。
- **验收条件**（AC-E-21🆕）：学员完成课程后，学员端显示的时长与报表「有效学习时长」**数值一致**。

## REQ-REC-03 学习时长口径
- **规则**【原站已验证 E017】：
  - 学习时长的计入由 **`模块 × 学习动作` 二维矩阵**决定（原文：「企业可根据自身情况，定义学习动作，平台基于开启情况，计算学习时长及学习人数」）。
  - **学习时长与学习人数共用同一套开关**，两指标同源。
  - **重复学习重复累计**（原文：「所有类型的知识，若重复学习将重复计算学习时长」）；完成后继续学习**仍累计**。
    - ⚠️ **精确含义（V-48 结案后修正）**：该规则作用于 **「累计学习时长」**；**「有效学习时长」封顶于内容标准时长**，不随重复学习增长。见 REQ-REC-04。
  - **【有意差异 DIFF-09】** 倍速播放时长倍速计算的开关**默认关闭**（按真实耗时计）。
  - ~~【DIFF-26】原站学习时长无上限可被刷~~ → ⚠️ **V-48 结案后修正**：原站**有**封顶机制（「有效学习时长」），见 REQ-REC-04。此前判断不完整。

## REQ-RPT-09 🆕 数据状态四态区分（取数失败绝不降级为 0）
- **业务目的**：让管理员能分辨"没有数据"与"系统故障"。
- **规则**【原站缺陷，明确不复刻，DIFF-29】：
  - 原站在统计接口失败时**把所有指标显示为 `0`**，无任何错误提示（2026-09-21 平台 502 期间实测）。
  - **V1 必须区分四态且视觉可辨**：

  | 状态 | 展示 | 触发条件 |
  |---|---|---|
  | 正常有值 | 数值 | 查询成功且有数据 |
  | 真实零值 | `0` | 查询成功，统计结果为 0 |
  | 无数据/不适用 | `--` | 查询成功但无记录；或比率的分母为 0 |
  | **取数失败** | **错误提示 + 重试入口** | 接口异常、超时 |

  - **取数失败时不得渲染任何数字**。
- **验收条件**（AC-E-14）：模拟统计接口 5xx → 看板显示错误提示与重试按钮，不显示任何数字；恢复后重试正常。

# 十三、面授中心（FTF）✅ **本期实施（D-38 前移）**

## REQ-FTF-01 面授对象与三步创建
- **规则**【E021】：`1 基本信息 → 2 更多设置 → 3 添加学员`
- 基本信息：面授名称(≤200，必填) / 关联培训计划 / 负责人 / **时长推送模式** / **授课时长（必填，发布后不可改）** / 授课讲师 / 授课课程 / 面授说明(≤1500)
- 列表字段：面授名称 / 状态 / **平台面授编号** / 来源 / 创建时间 / 更新时间 / 面授开始时间 / 面授结束时间 / 负责人
- **验收**：授课时长在面授发布后置灰不可改（REQ-GLOBAL-02）。

## REQ-FTF-02 时长推送模式
- **规则**【E021 §3，原文】：
  - **即学即推**：「完成面授任务后，系统即刻推送授课时长给学员或者讲师」
  - **核实下发**：「完成面授任务后，管理员需要核对并填写实际时长，然后再将时长推送给学员或者讲师」
- **规划要求**：与在线课堂的「学分发放时机」抽象为**统一的发放策略机制**，不要每模块各写一套。
- **验收**：设"核实下发" → 面授结束后学时处于待核实状态，管理员填写实际时长后才发放。

## REQ-FTF-03 场次
- **规则**【E021 §4】：场次名称(≤200) / 场次时间(必填) / 上课地址(**定位选择**，≤300，可设为常用地址) / 场次考勤(签到、签退各自可勾选，勾选后必须完成才算本场次考勤)
- **上限：最多 15 个场次**；按场次开始时间正序排序。
- **验收**：添加第 16 个场次被拒绝。

## REQ-FTF-04 考勤规则
- **规则**【E021 §5】：
  - **签到/签退时间范围为四个独立参数**：开始前 N 分钟、开始后 N 分钟（签到）；结束前 N 分钟、结束后 N 分钟（签退）
  - `学员需要扫考勤码才能签到`
  - **`开启签到电子围栏`**（地理位置校验）
  - **`学员请假需要审批`** + `审核流程设置`
- **验收**：① 超出签到时间范围无法签到；② 开启电子围栏后，位置不在范围内签到被拒。

## REQ-FTF-05 请假状态
- **规则**：**「请假」是一等学员状态，带审批流**。签到大屏的"一键催促未签到学员"**不包含请假学员**（E018 §6.1）。
- **验收**：学员请假获批后，不出现在催促名单中，且其未签到不计为缺勤。

## REQ-FTF-06 面授完成标准（V-58 已解答）
- **规则**【E021 §7.2，网页实测】：
  ```
  面授完成标准 = 组合逻辑(满足所有条件 | 满足任意条件) × 条件项
  条件项仅两个：① 完成场次考勤  ② 录入面授考核成绩
  ```
  - **强制校验**：至少选择一项，否则提示「请至少选择一项」且无法继续。
- **关键**：条件项**只有两个，不是开放集合** —— 手册写"…等"是笼统表述，实际就这两项。**按两项实现即可，不必做可扩展条件引擎。**
- **衍生要求**：「录入面授考核成绩」意味着面授有**成绩录入环节**（管理员/讲师录入），面授学员记录需含 `考核成绩` 与 `录入人` 字段。
- ⭐ **前置依赖（E021 §9 实测）**：**「完成场次考勤」只有在至少一个场次启用了签到或签退时才可选**；否则为禁用态并提示「**所有场次均未设置考勤**」。
  → **这个设计值得复刻**：在 UI 层以禁用态+原因提示做前置约束，比"选了之后保存报错"体验好得多。
- **验收**：① 不选条件无法保存；② 设"满足所有条件"+两项 → 仅签到未录成绩时不算完成；③ **所有场次都没设考勤时，「完成场次考勤」不可选且给出原因**。

## REQ-FTF-07 面授评价与结束设置
- **规则**【E021 §7.1/7.3】：
  - 面授评价：`学员评价`（评讲师）/ `讲师评价`（评学员）—— **双向**，问卷由调查中心提供
  - `自动结束面授`
  - **`面授授课核实通知设置`**：原文「面授任务结束后，系统将提醒负责人核实实际授课情况」—— 与 REQ-FTF-02 的 `核实下发` 模式配套
- ⚠️ **D-35 后再次变更**：审核中心已进需求池，**面授请假回到「单级固定审批」的最简实现**，不接通用审批流引擎。**须显式声明。**
