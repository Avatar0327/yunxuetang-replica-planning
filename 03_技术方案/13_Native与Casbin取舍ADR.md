# ADR-001：Native 与 Casbin 的权限实现取舍

日期：2026-09-23｜状态：技术建议形成，当前门禁No-Go；待业务/项目负责人评审｜依据：[权限预研报告](12_权限预研报告.md)

**建议以集中式 Native PolicyService 作为后续整改候选，保留 Casbin 对照；两套候选参考性能均未达标，当前不能放行正式开发。** 这是已选技术栈 A 内的权限实现取舍，不更换 Vue/NestJS/PostgreSQL/Redis，也不启动正式 B1。

## 1. 决策问题与约束

T-05 要求角色内人员覆盖后，同节点同动作多角色并集；字段能力绑定实际匹配对象的来源。T-06 要求任命派生后台入口和精确项目权限；T-07 要求客户公司硬上限。六范围、等级与选定管理角色转授、历史事实公司、分类继承、严格下一请求撤权和故障拒绝均已裁定，不能为了适配引擎删减。

两个候选用同一真实数据、业务策略、SQL、节点字典、账号/公司边界、权威版本和故障协议；本轮比较的是这两个**具体适配实现**，不是对 Casbin 产品所有模型和优化方案的判决。

## 2. 实际实现与比较

| 项目 | Native 候选 | Casbin 候选 | 实际意义 |
|---|---|---|---|
| 真正执行的引擎 | 显式匹配 tenant/actor/node/action/revision/source | node-casbin 5.38.0，真实 model/policy/enforce；不读取 Native 的最终允许值 | 两者不是同一函数改名字 |
| 单对象语义 | 来源逐一匹配，保留 matched source/field | 同一组织范围谓词作为 scopeForSource，自主 enforce 后收集匹配来源 | 对象授权、字段来源真值双候选执行 |
| 列表路径 | 选择对应节点动作的有效来源 | 实际创建 enforcer、添加策略，逐来源 enforce 选择有效来源 | 每来源匹配不等于每数据行鉴权；都未用 N+1 替代 SQL |
| 数据行/字段处理 | 共同 QueryPolicy 与参数化 SQL 编译器 | 同左 | 角色覆盖、范围/公司交集、CASE 原值字段、count/分页/聚合仍需本项目实现 |
| 来源生命周期 | 共同成员/分类来源、保存上限、冻结与重验 | 同左 | 框架并未消除转授集合语义和依赖变更工作 |
| 撤权与故障 | 共同 DB 权威 revision、Redis 必需健康、提交锁序、worker/媒体重验 | 同左；没有将 watcher/PubSub 当可靠撤权机制 | 不能通过切换 matcher 修复共同协议缺陷 |
| 本次缓存 | 授权快照缓存，版本约束 | 同样快照；enforcer 当前逐请求创建，没有版本绑定复用 | 性能结论只适用于本次实现，不是 Casbin 最佳性能上限 |
| 维护成本 | 来源匹配逻辑直接、类型与业务契约一致；自行维护完整正确性责任 | 额外模型/策略与 adapter 维护，公共业务自研仍保留；具有通用引擎能力 | 本项目尚未测得可量化维护人天节省，不虚构收益 |

核心代码：`src/authz/bulk-candidate.ts` 是实际 HTTP 列表来源选择；`candidates.ts` 是对象语义对照；`policy.ts/scope.ts/compiler.ts/revision.ts/cache.ts` 是共同业务/查询/撤权骨架。它们随源码归档交付，不把对象微基准充作 HTTP 性能。

## 3. 证据与结论

双方冻结源码在语义/SQL/公司隔离/字段/导出/撤权/故障和真实浏览器流程上完成相同验证。最终代码审查关闭四项 Important，仍有可读性 Minor；复杂性能见下表。

单位均为毫秒；p95仅来自成功请求。权限门槛50、列表500、历史聚合2000。

| 候选/缓存 | 成功/总请求 | 非成功率 | 权限p95范围（四场景） | 列表p95范围 | 宽/复杂历史p95 | 结论 |
|---|---:|---:|---|---|---|---|
| native/hot | 8990/9129 | 1.52% | 1423.73～1717.71 | 1974.88～2368.35 | 5960.14/10346.87 | 未通过 |
| native/cold | 9095/9174 | 0.86% | 1471.26～1736.15 | 1904.01～2263.67 | 5891.03/10200.46 | 未通过 |
| casbin/hot | 8212/8557 | 4.03% | 1461.79～1794.74 | 2068.16～2591.76 | 6494.93/10386.04 | 未通过 |
| casbin/cold | 2533/4003 | 36.72% | 2400.98～3220.19 | 3387.58～4845.42 | 10563.66/12191.90 | 未通过 |

四个参考窗口合计 30,863 次请求，成功 28,830 次，非成功 2,033 次；非成功HTTP/传输分类为 {'503': 1789, 'transport_exception': 244}。成功结果真值差异与记录到的授权错误均为 0，测量错误 0；各窗口均未满足原性能门槛，不能凭语义正确放行。 两候选共用大部分权限/查询路径，因此本次结果首先说明当前方案整体需要整改。

建议 Native 的理由是当前 Casbin 只减少了基础来源匹配的自写部分，却仍需同一套非通用业务规则、批量查询和版本协议；Native 的这段匹配更直观，便于“本人＋AI”维护和审查。**不把两候选的延迟差全部归因于 matcher，也不把共享实现的问题归咎于 Casbin。** 当前没有配对微观剖析来证明各组件占比，不能承诺只换引擎即可达标。

若将来出现跨产品统一策略管理、可复用 adapter 或实测显示版本绑定 enforcer 有明显维护收益，可以重开 ADR，仍须用完整双候选真值、两实例撤权、故障和参考窗口复验。不得以引擎产品宣传替代本项目结果。

## 4. 后续设计边界与门禁

下一轮先增加权限构建、序列化/解析、事件循环、池等待和数据SQL的分段观测；比较版本绑定的许可关系/计划与直接关系查询，避免每请求搬运大人员/公司数组。允许提出索引或表示优化，但必须保存原真值、来源字段和版本边界，使用同资源完整冷热窗口及撤权/故障回归证明。未实际验证前不选定某个新Schema为正式实现。

共同硬约束保持：每个受保护新请求读取权威当前版本与账号状态；Redis 故障拒绝；角色内覆盖/同动作并集、公司上限和字段来源不变；受保护媒体和导出不得通过旧链接绕过；权限判定集中。任何缓存复用都必须绑定版本并有资源界限，不能删掉撤权检查换取性能。

正式估算沿用 11 的分列。B1-05/B1-07 原 8～13 的条件重估为 14～25，净增 6～12；B1-08 原 2～3 另列，不将 A 已计的 T-05/T-07/T-16 再收费。原型折抵 0；后续新增整改预研 2～4 若采用须独立记录。它们都是条件估算，不是选 Native 自动获批的追加工期。

五项永久缺口 G-01/G-02/G-04/G-05/G-06 不销项；D-42/T-10 为我方定义、原站未验证。正式 B1 不因本 ADR 或文档齐全自动放行。
